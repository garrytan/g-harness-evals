# Ubicloud check lane

`pr-check.sh <pr-number>` runs the keyless checks of [ci.yml](../../.github/workflows/ci.yml) for one pull request on an ephemeral Ubicloud VM and posts the verdict as the commit status `ubicloud/checks` on the head sha, so a pull request can go green while GitHub Actions is out of minutes or queued. `bootstrap.sh` mirrors the workflow's runner (Bun at the workflow's `bun-version`, python3, jq, Docker); `checks.sh` runs the workflow's steps in its order and stops at the first failure with that step's exit code (`bun install --frozen-lockfile`, `bunx tsc --noEmit`, `bun test tests/`, `python3 scripts/check-links.py`, `bun runner/prereg/prereg.ts`, then `bun scripts/seal-heldout.ts --check`, then the `docker-e2e` steps when `docker-applies.sh` says the workflow would run them: the image build and `tests/gbrain-image.test.ts`). The VM is standard-8, or standard-16 when the docker job applies; a sha that already carries a success or failure status is not rerun without `--force`. When no VM could be created because the project's vCPU quota is exhausted, the status is `error` ("no VM: the Ubicloud vCPU quota is exhausted; rerun when it frees") and the script exits 3; an `error` status is not cached, so the rerun needs no `--force`. A VM run that ended before the checks reported a result, or a log with no `checks:` line, posts `failure` the same way. `ubi-runner.sh` is the runner from the Ubicloud skill (one VM per run, destroyed on every exit path); it needs `UBICLOUD_API_KEY` in the environment, and `UBI_OWNER` set to the caller's thread code names the VM after its owner. Logs go to `--log-dir` (default `HE_CI_LOG_DIR` or `~/.local/state/harness-evals/ci-logs`) as `<pr>-<sha>.log`, one timestamped line per output line, with the runner's phase markers from which the status description takes the VM start, bootstrap and checks durations. Run several pull requests as separate background processes; each is its own VM. `pr-check.sh <pr> --relink URL` posts the head's existing final status again with URL as its link and runs nothing; it exits 1 when the head has no final status and 2 when the status cannot be read. Nothing here prints or stores a key.

`pr-watch.sh` is the lane's head discovery: each cycle it lists the open non-draft pull requests against main (`--drafts` includes drafts), reads the `ubicloud/checks` status on every head, and runs `pr-check.sh` on each head that has no status or has been pending longer than `--stale-pending` (45 minutes, a run that died with its machine); heads with success, failure or error are left alone (`--retry-errors` retries a quota refusal), and `pr-check.sh` runs without `--force`, so its own cache still refuses a head that gained a verdict in the meantime. A head whose status GitHub failed to return (or whose timestamp does not parse) is skipped for the cycle and named on stderr rather than read as unchecked, and a cycle whose pull request list cannot be read exits 1. `--once` is one cycle, the form a poll runs; without it the loop sleeps `--interval` (300 s) between cycles and exits after the first cycle that ran a check or after `--max-seconds`, so a caller that waits on the process is woken to read the results. One instance runs per log directory. It exists because the two heads the lane missed on 2026-10-26 (#77 at d7baf4d, #82 at a3ede55) were pushed while the operator's thread was asleep: discovery was a human step, and it is now a script step. Before each cycle it sweeps this owner's check VMs: `pr-check.sh` names its VM `ubirun-<owner>-<epoch>-pr<n>` with the owner id `ubi-runner.sh owner` derives, and `--reap-after MINUTES` (60; 0 disables; anything but whole minutes exits 2) destroys every such VM older than that whose controlling process is not alive on this machine (ubi-runner's local state names it; state written before this machine last booted counts as a dead controller, whatever process holds the pid now), repeating ubi-runner's lines on stdout as the receipt and waiting at most `UBI_DOWN_TIMEOUT` (120 s; an inherited value must be whole seconds without a leading zero, or the watcher exits 2 while the sweep is on) per VM; `--dry-run` prints `would destroy` instead. Shard VMs carry no `-pr` suffix and another owner's VMs are never listed, so neither is touched; a check VM from another thread's machine is not this watcher's to sweep, which is why the check lane runs from the lane machine only (docs/ubicloud.md, Limits). A check VM started under the lane's own owner id from another machine has no local state here and is swept at the same age, so that owner id belongs to the lane machine alone. A missing runner or a failed `list --mine` is said on stdout with ubi-runner's last line and the cycle goes on. `UBI_RUNNER` overrides the runner the way it does for `pr-check.sh`; the tests keep the sweep off the network with `--reap-after 0`.

`merge-pass.sh` is the crew's merge rule as a script (CREW.md, "Who merges" and "Ship before merge"): for every open pull request against main it merges with `gh pr merge --squash --match-head-commit <head>` only when the pull request is not a draft, GitHub reports it MERGEABLE and CLEAN, every check is pass or skipping with the `checks` job among them, the newest `ubicloud/checks` status on the head is success, and the body's last `GSTACK_RESULT: skill=ship status=<s>` line has a whole status token in the allowlist (complete, pass, passed, ok, success, shipped) and names the head, as the full sha or its first 12 characters, on that line or on a `head: <sha>` line within the next two lines. The gate trusts whoever can edit the body, as the crew rule does. Anything else is a skip with its reason on stdout; the branch is never deleted; `--match-head-commit` makes GitHub refuse a merge when a push landed between the checks and the merge. Each merge appends `<UTC> #<n> merge <merge sha> head <head sha>` to `--merge-log` (`HE_MERGE_LOG`) before the merged line is printed; a log that cannot be written is said on stderr, and GitHub's merge commit stays the record of truth. `--dry-run` prints `would merge` and merges nothing; every gh call is bounded by 60 s. It replaced the untested poll script on internal-task's machine after the autoplan review of 2026-10-27 found that script's receipt check was a status denylist with the head sha grepped anywhere in the body and its merge unbound to the inspected head.

`pr-watch.sh --until-change` is the wake-on-change mode the lane runs in (CREW.md, Token efficiency: never poll with agent wake-ups). The loop stays up across cycles without events, keeps check, sweep and merge-pass decisions in the log (`--verbose` adds `nothing due` lines), runs `merge-pass.sh` after the checks of each cycle when `--merge` is given (`--merge-log` is its log), and, unless `--once` ends it after one cycle, exits 0 with one `EVENT:` line per thing an operator must read: `check-finished #<n> <sha12> <verdict>` (the sha the verdict names, the head `pr-check.sh` checked), `merged #<n> <sha12> <merge sha>`, `merge-failed #<n> <sha12> <gh's last line>` when GitHub refused a merge the rule allowed, `awaiting-receipt #<n> <sha12>` the first time a green pull request is skipped only for its missing ship receipt (remembered per head in `--log-dir`, so the agent tells the author once, as CREW.md asks), `failure #<n> <sha12> pr-check exit <rc> with no verdict line`, `failure gh-pr-list failed on 2 consecutive cycles (exit <rc>)` (one failure is retried next cycle), `failure merge-pass failed on 2 consecutive cycles (exit <rc>)`, `reaped <location>/<vm>`, or `max-age <seconds>` when `--max-seconds` passed with nothing else to report. `--max-seconds` (20000 by default) stays under the six-hour ceiling of a Capy background operation, so a quiet loop ends with `max-age` and a relaunch rather than a killed operation. The lane machine starts it as a background operation and its agent waits on that operation alone, with no timer; after an event the agent copies the lane log into the drives, relinks the status, reports the event in one line and starts the loop again. Without the flag the loop behaves as before.

The same directory holds the shard lane for counted runs, `run-shard.sh`, `vm-shard.sh` and `fanout.sh` (one standard-16 VM per shard, the repository pinned at the preregistration commit, the smoke, `scripts/run-shard.sh`, results copied back, VM destroyed), described in [docs/ubicloud.md](../../docs/ubicloud.md).
