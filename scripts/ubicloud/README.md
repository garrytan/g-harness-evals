# Ubicloud check lane

`pr-check.sh <pr-number>` runs the keyless checks of [ci.yml](../../.github/workflows/ci.yml) for one pull request on an ephemeral Ubicloud VM and posts the verdict as the commit status `ubicloud/checks` on the head sha, so a pull request can go green while GitHub Actions is out of minutes or queued. `bootstrap.sh` mirrors the workflow's runner (Bun at the workflow's `bun-version`, python3, jq, Docker); `checks.sh` runs the workflow's steps in its order and stops at the first failure with that step's exit code (`bun install --frozen-lockfile`, `bunx tsc --noEmit`, `bun test tests/`, `python3 scripts/check-links.py`, `bun runner/prereg/prereg.ts`, then `bun scripts/seal-heldout.ts --check`, then the `docker-e2e` steps when `docker-applies.sh` says the workflow would run them: the image build and `tests/gbrain-image.test.ts`). The VM is standard-8, or standard-16 when the docker job applies; a sha that already carries a success or failure status is not rerun without `--force`. `ubi-runner.sh` is the runner from the Ubicloud skill (one VM per run, destroyed on every exit path); it needs `UBICLOUD_API_KEY` in the environment, and `UBI_OWNER` set to the caller's thread code names the VM after its owner. Logs go to `--log-dir` (default `HE_CI_LOG_DIR` or `~/.local/state/harness-evals/ci-logs`) as `<pr>-<sha>.log`, one timestamped line per output line, with the runner's phase markers from which the status description takes the VM start, bootstrap and checks durations. Run several pull requests as separate background processes; each is its own VM. Nothing here prints or stores a key.
