# Ubicloud check lane

`pr-check.sh <pr-number>` runs the keyless checks of [ci.yml](../../.github/workflows/ci.yml) for one pull request on an ephemeral Ubicloud VM and posts the verdict as the commit status `ubicloud/checks` on the head sha, so a pull request can go green while GitHub Actions is out of minutes or queued. `bootstrap.sh` mirrors the workflow's runner (Bun at the workflow's `bun-version`, python3, jq, Docker); `checks.sh` runs the workflow's steps in its order and stops at the first failure with that step's exit code (`bun install --frozen-lockfile`, `bunx tsc --noEmit`, `bash scripts/run-tests.sh` (`bun test tests/` in parallel phases; plain `bun test tests/` on a head without the script), `python3 scripts/check-links.py`, `bun runner/prereg/prereg.ts`, then `bun scripts/seal-heldout.ts --check`, then the `docker-e2e` steps when `docker-applies.sh` says the workflow would run them: the image build and `tests/gbrain-image.test.ts`). The VM is standard-8, or standard-16 when the docker job applies; a sha that already carries a success or failure status is not rerun without `--force`. When no VM could be created because the project's vCPU quota is exhausted, the status is `error` ("no VM: the Ubicloud vCPU quota is exhausted; rerun when it frees") and the script exits 3; an `error` status is not cached, so the rerun needs no `--force`. A VM run that ended before the checks reported a result, or a log with no `checks:` line, posts `failure` the same way. `ubi-runner.sh` is the runner from the Ubicloud skill (one VM per run, destroyed on every exit path); it needs `UBICLOUD_API_KEY` in the environment, and `UBI_OWNER` set to the caller's thread code, which the VM is named after (a check refuses to start without it; `--relink` makes no VM and does not need it). Logs go to `--log-dir` (default `HE_CI_LOG_DIR` or `~/.local/state/harness-evals/ci-logs`) as `<pr>-<sha>.log`, one timestamped line per output line, with the runner's phase markers from which the status description takes the VM start, bootstrap and checks durations. Run several pull requests as separate background processes; each is its own VM. `pr-check.sh <pr> --relink URL` posts the head's existing final status again with URL as its link and runs nothing; it exits 1 when the head has no final status and 2 when the status cannot be read. A pull request whose head or base branch is the orphan branch `custody` exits 2 before any status read, post or fetch, with the branch named on stderr (coordinating agent, 2026-10-28: the lane never checks out or merges `custody`). Nothing here prints or stores a key.

`pr-watch.sh` is the lane's head discovery: each cycle it lists the open non-draft pull requests against main (`--drafts` includes drafts), reads the `ubicloud/checks` status on every head, and runs `pr-check.sh` on each head that has no status or has been pending longer than `--stale-pending` (45 minutes, a run that died with its machine); heads with success, failure or error are left alone (`--retry-errors` retries a quota refusal), and `pr-check.sh` runs without `--force`, so its own cache still refuses a head that gained a verdict in the meantime. A pull request with the orphan branch `custody` as its head or base is skipped before the draft and status filters in every mode, with a `skipped` line in the log, and pull requests into `custody` are listed beside the `--base` list so they are seen at all (GitHub filters a list by base); the `--until-change` paragraph below says how the loop reports such a head. A head whose status GitHub failed to return (or whose timestamp does not parse) is skipped for the cycle and named on stderr rather than read as unchecked, and a cycle whose pull request list cannot be read exits 1. `--once` is one cycle, the form a poll runs; without it the loop sleeps `--interval` (300 s) between cycles and exits after the first cycle that ran a check or after `--max-seconds`, so a caller that waits on the process is woken to read the results. One instance runs per log directory. It exists because the two heads the lane missed on 2026-10-26 (#77 at d7baf4d, #82 at a3ede55) were pushed while the operator's thread was asleep: discovery was a human step, and it is now a script step. Before each cycle it sweeps this owner's check VMs: `pr-check.sh` names its VM `ubirun-<owner>-<epoch>-pr<n>-t<hours>` (no `-t<hours>` before 2026-10-30) with the owner id `ubi-runner.sh owner` derives and the TTL `ubi-runner.sh ttl` prints (3 hours unless `UBI_TTL_HOURS` is set), and `--reap-after MINUTES` (60; 0 disables; anything but whole minutes exits 2) destroys every such VM older than that whose controlling process is not alive on this machine (ubi-runner's local state names it; state written before this machine last booted counts as a dead controller, whatever process holds the pid now), repeating ubi-runner's lines on stdout as the receipt and waiting at most `UBI_DOWN_TIMEOUT` (120 s; an inherited value must be whole seconds without a leading zero, or the watcher exits 2 while the sweep is on) per VM; `--dry-run` prints `would destroy` instead. Shard VMs carry no `-pr` suffix and another owner's VMs are never listed, so neither is touched; a check VM from another thread's machine is not this watcher's to sweep, which is why the check lane runs from the lane machine only (docs/ubicloud.md, Limits). A check VM started under the lane's own owner id from another machine has no local state here and is swept at the same age, so that owner id belongs to the lane machine alone. A missing runner or a failed `list --mine` is said on stdout with ubi-runner's last line and the cycle goes on. `UBI_RUNNER` overrides the runner the way it does for `pr-check.sh`; the tests keep the sweep off the network with `--reap-after 0`.

`merge-pass.sh` is the crew's merge rule as a script (CREW.md, "Who merges" and "Ship before merge"): for every open pull request against main it merges with `gh pr merge --squash --match-head-commit <head>` only when the pull request is not a draft, GitHub reports it MERGEABLE and CLEAN, every check is pass or skipping with the `checks` job among them, the newest `ubicloud/checks` status on the head is success, and the body's last `GSTACK_RESULT: skill=ship status=<s>` line has a whole status token in the allowlist (complete, pass, passed, ok, success, shipped) and names the head, as the full sha or its first 12 characters, on that line or on a `head: <sha>` line within the next two lines. The gate reads no review depth or panel field, so a receipt from a /ship with no panel (R65: docs, results, finding files, prereg prose) passes like any other. A body line `INTERIM_GATE: reviewer=<model> head=<full sha> pregate=pass` naming the exact current head is accepted in place of the receipt only when the pull request was opened, and the head's earliest commit status was created, before 2026-10-31T07:00:00Z (00:00 PT), when the /ship gate came back (both times GitHub sets, unlike a commit's backdatable dates; a failed status read is its own skip, retried next cycle) (CREW.md "/ship gate RESTORED"); a newer head waits for its receipt, and a valid receipt still passes alone. The gate trusts whoever can edit the body, as the crew rule does. Anything else is a skip with its reason on stdout; the branch is never deleted; `--match-head-commit` makes GitHub refuse a merge when a push landed between the checks and the merge, and the head sha and both branch names are read again right before the merge call, so a head that moved or a base that changed since the list (a retarget to `custody` included) is a skip, since `gh pr merge` binds the head and not the base. Each merge appends `<UTC> #<n> merge <merge sha> head <head sha> gate <ship-receipt status=<s> | interim-gate reviewer=<model>>` to `--merge-log` (`HE_MERGE_LOG`) before the merged line is printed; a log that cannot be written is said on stderr, and GitHub's merge commit stays the record of truth. `--dry-run` prints `would merge` and merges nothing; every gh call is bounded by 60 s. It replaced the untested poll script on the lane machine after the autoplan review of 2026-10-27 found that script's receipt check was a status denylist with the head sha grepped anywhere in the body and its merge unbound to the inspected head.

`merge-pass.sh --land` (or `HE_LAND=1`, which `pr-watch.sh --merge` passes through) is the merge for a base whose `.gstack/ship-policy.json` sets `changelog_fragments` (gstack docs/ship-policy.md, "gstack-ship-queue land"): pull requests carry a `changelog.d/` fragment and no version, so nobody re-ships to renumber after another merge. Every check above still runs first. A pull request whose head P is the head its receipt names is made READY on a detached checkout of P (`bun install --frozen-lockfile` when the pin has a `package.json`, since a fresh worktree has no `node_modules`, then `gstack-pregate run` and `gstack-ship-queue ready`, with the five API key variables and the lane's own settings unset (`HE_*` such as `HE_MERGE_HOLD` and `HE_CI_LOG_DIR`, and `UBI_*` such as `UBI_OWNER` and `UBI_TTL_HOURS`; the list is `pinned()` in the script), and `bun install` under a 900-second timeout, so the pin's own lane tests and its pregate see a clean environment) and landed with `gstack-ship-queue land --pr <n> --no-wait`, which pushes land's stamp commit S, with parents P and the base tip, and stops; that pass prints `stamped <S12> (land)` and merges nothing. `pr-watch.sh` checks S like any new head. A later pass merges S only when S has exactly two parents, the first is the head the receipt names and the second is the base tip just fetched; when that merge is clean and `gstack-tree-receipt` compares S with it as `TREE: same-modulo-stamps`; and when the checks above pass at S itself. The merge is then `land --pr <n>`, which resumes from its journal, re-reads the receipt and checks, and squashes with `--match-head-commit` S. The merge-log gate ends `land-stamp pin <P12>`. A land that returns without merging (its checks at S still pending) is a skip, and a failed land is `merge failed: land: <reason>`, which `pr-watch.sh` reports as a merge failure. When S merged a base tip that has moved since and still passes the MERGEABLE/CLEAN and check gates above, the pass resumes `land --pr <n> --no-wait`, whose journal restamps P on the new tip, and prints `restamped <S12> (land)`. GitHub reports a stale stamp, or a pin cut before another merge, CONFLICTING/DIRTY once VERSION and CHANGELOG.md move on main; when `git merge-tree` finds no conflict outside VERSION, `package.json` and CHANGELOG.md the pass stamps or restamps it all the same (land resolves those fields, and the line adds `over release-field conflicts (<files>)`), and any other conflict, or BEHIND, is still a skip. A fetch that fails in the stamp or conflict check is its own skip, retried next cycle. P is fetched from the pull request ref before the READY checkout, so a fresh land checkout works, and a fork pull request is a skip before any of its code is fetched or run, since land stamps and pushes only crew branches. Anything else is a skip with its reason. land runs in `HE_LAND_CHECKOUT` (default the repository root), which must be a checkout on the base branch, and gstack's tools come from `GSTACK_BIN` (default `~/.local/share/gstack/bin`); a missing one is exit 2. Under `"merge": "direct"` in main's `.gstack/ship-policy.json` (gstack v1.95.0.0, docs/ship-policy.md "land --pin"; read from the fetched base each pass) there is no stamp: a pull request that passes every check at its own head is made READY the same way and merged with `gstack-ship-queue land --pr <n> --pin <head>`, which also needs the /ship receipt in the body and a diff that leaves VERSION, the `package.json` version and CHANGELOG.md alone; the merge-log gate ends `land-pin`. In this mode only, when the body's last `GSTACK_RESULT` line passes but names an older head, the head also passes when the body's `gstack-ship-receipt` block has `pr` set to this pull request and `head` set to the current head (12 or more characters), since `gstack-ship-receipt carry` rewrites that block and never the hand-written line; READY and land --pin bind the block again, and the gate then reads `ship-receipt-block status=<s>`. A body whose `gstack-ship-receipt` block does not name the head, or a head that changed VERSION, CHANGELOG.md, `.gstack/version-path` or the `package.json` version since its merge base, is a skip before READY (land --pin refuses both, and READY runs the whole pregate), and the hold file and the closing-keyword check are read again after READY, right before land --pin. A conflicting head never lands, and a stamp left from train mode (two parents, the first a receipted pin, the second on main, its tree differs from their clean merge, and `gstack-tree-receipt` calls it same-modulo-stamps against that merge) is a skip that says `reset the branch to <P12>`, since that pin's receipt still holds and a stamp cannot land; a plain base merge, whose tree is that clean merge, needs a receipt of its own (`gstack-ship-receipt carry` writes one), and any other merge commit needs a new /ship. Direct mode tests each pull request at its own head only, so two pull requests that pass alone can still break main together; main's own checks after each merge are what catch that. Versions move only in the release PR (`gstack-release-stamp open`), which has no ship receipt, so the lane skips it and the coordinating agent lands it by hand. Approved on 2026-11-02 under the R40 fix lane ([changelog.d/README.md](../../changelog.d/README.md) is the author side).

Merge holds (CREW.md, "Prereg merge holds") are a file, not a memory: `merge-pass.sh --hold-file <file>` (or `HE_MERGE_HOLD`, which `pr-watch.sh --merge` passes through) reads one hold per line, `pr=<n> <why>`, as a queue in file order. While GitHub reports the first line's #<n> open, every other pull request that passes the whole rule is skipped as `held until the hold lifts` and only #<n> itself may merge; once #<n> is merged or closed its line lifts itself and the next open line takes over, so a file of `pr=149`, `pr=148`, `pr=150` merges those three in that order before anything else. A line that does not start with `pr=<n>`, or a state that cannot be read, holds everything (so a freeze note that mentions `apr=5` still holds everything), and `pr=0149` names #149. A hold file that exists but cannot be read (a directory, a dangling link), or one whose directory is missing or unreadable (the drive not mounted), is exit 1 with nothing merged, NUL bytes or UTF-16 never hide a hold, and the file is read again right before each merge so a hold written during the pass still stops it; a named file that does not exist in a readable directory holds nothing, and each pass prints `merge-pass: no hold file at <path>, so nothing is held` so a missing drive shows in the log. `--pr <n>` (or `#<n>`) passes over one pull request only, so a merge by hand goes through the same rule and the same holds; a number that is not an open pull request against the base is said and exits 1, and a hand merge needs `--hold-file` or `HE_MERGE_HOLD` set to see the holds. `pr-watch.sh --merge` fails closed without the file: with neither `--hold-file` nor `HE_MERGE_HOLD` it exits 2, it passes the file on as `--hold-file`, and a cycle that finds no file at that path runs no merge pass; the first such cycle ends with a `failure hold-file <path> is missing; nothing merged` event, raised again only after a cycle has found the file in between. Each cycle it also checks the active hold's head first, and skips the frozen constituents a train's line names with `frozen=<m>[,<m>...]` (`skipped, frozen, a constituent of train #<n>`). The merge lane keeps its hold file at `handoffs/internal-task/MERGE_HOLD` in the project's private drive.

Closing keywords (CREW.md, 2026-11-03): GitHub closes an issue or pull request that a merged title, body or squash message names after close, closes, closed, fix, fixes, fixed, resolve, resolves or resolved (any case, an optional colon, then `#<m>`, `GH-<m>`, `<owner>/<repo>#<m>` or its URL); #245's "Fix #244's open notes" closed #244 unmerged. Right before any stamp or merge `merge-pass.sh` reads the title, the body and every commit message (from 100 commits through the paginated REST list, since `gh pr view` stops at 100; 250 or more is a skip), which the squash message is built from, and skips a pull request whose closing keyword names an open issue or pull request, or one whose state it cannot read, naming the reference and where it is; the pull request's own number does not count. After a merge it says and logs (`<UTC> #<n> closed <owner/repo>#<m> on merge <sha> (<why>)`) each issue GitHub linked as closing and each reference in the merge commit's own message that is now closed.

`pr-watch.sh --until-change` is the wake-on-change mode the lane runs in (CREW.md, Token efficiency: never poll with agent wake-ups). The loop stays up across cycles without events, keeps check, sweep and merge-pass decisions in the log (`--verbose` adds `nothing due` lines), runs `merge-pass.sh` after the checks of each cycle when `--merge` is given (`--merge-log` is its log), and, unless `--once` ends it after one cycle, exits 0 with one `EVENT:` line per thing an operator must read: `check-finished #<n> <sha12> <verdict>` (the sha the verdict names, the head `pr-check.sh` checked), `merged #<n> <sha12> <merge sha> (gate: <gate>)` (merge-pass.sh's merged line passed through, so the event says which gate admitted the merge), `merge-failed #<n> <sha12> <gh's last line>` when GitHub refused a merge the rule allowed, `awaiting-receipt #<n> <sha12>` the first time a green pull request is skipped only for its missing ship receipt (remembered per head in `--log-dir` when the event prints, and only by the `--until-change` loop, so the agent tells the author once, as CREW.md asks, and a loop killed mid-cycle or a plain `--once --merge` cycle does not consume the report), `custody-skip #<n> <sha12> custody is the <head|base|head and base> branch` the first time a pull request with the orphan branch `custody` as its head or base is seen (the coordinating agent's 2026-10-28 rule: that branch holds sealed ciphertext and the key escrow and is never checked out, checked or merged by the lane; GitHub filters a pull request list by base, so pull requests into `custody` are listed beside the `--base` list to be seen at all, the head list skips a custody head or base before the draft and status filters, `merge-pass.sh` skips it before any other read and again on the fresh read before each merge, `pr-check.sh` refuses it with exit 2, and the agent reports it to the coordinating agent once per head, remembered only by the `--until-change` loop that prints the event, so a plain or `--dry-run` cycle on the same log directory does not consume the report), `failure #<n> <sha12> pr-check exit <rc> with no verdict line`, `failure gh-pr-list failed on 2 consecutive cycles (exit <rc>)` (one failure is retried next cycle), `failure merge-pass failed on 2 consecutive cycles (exit <rc>)`, `reaped <location>/<vm>`, or `max-age <seconds>` when `--max-seconds` passed with nothing else to report. `--max-seconds` (20000 by default) stays under the six-hour ceiling of a Capy background operation, so a quiet loop ends with `max-age` and a relaunch rather than a killed operation. The lane machine starts it as a background operation and its agent waits on that operation alone, with no timer; after an event the agent copies the lane log into the drives, relinks the status, reports the event in one line and starts the loop again. Without the flag the loop behaves as before.

The same directory holds the shard lane for counted runs, `run-shard.sh`, `vm-shard.sh` and `fanout.sh` (one standard-16 VM per shard, the repository pinned at the preregistration commit, the smoke, `scripts/run-shard.sh`, results copied back, VM destroyed), described in [docs/ubicloud.md](../../docs/ubicloud.md).
