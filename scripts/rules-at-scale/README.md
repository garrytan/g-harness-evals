# Rules at scale: build files

**Does each coding agent still follow its rules file (CLAUDE.md, AGENTS.md) as the file grows?** These files build the eval's rules files and grade its trials. The plan and its preregistration live under docs/benchmarks/ once they are written.

- `rules.json`: the six planted rules, word for word, the three rotations that put each rule at the top, middle and end of the file equally often, the neutral section headings, the file name each harness reads and the size ladder.
- `corpus/`: the filler. Real rules files from public, permissively licensed repositories (`files/`, pinned by commit in `sources.json`, licences in `LICENSES/`, summary in `NOTICES.md`), filtered so no line touches a planted rule's topic (`DROPS.md`, `drop-list.json`) and drawn in one seeded order (`filler.json`). `crawl.ts` collects candidates from GitHub code search; `build-corpus.ts` selects and rebuilds.
- `sizes/SIZES.md`: how big public AGENTS.md and CLAUDE.md files are, and how many sit past each harness's cut.
- `materialize.ts`: writes one arm's rules files for one task and harness, plus `manifest.json` with every rule's byte offset.
- `grade.ts`: grades one trial: each rule met, not met, not applicable or unscorable, and for each captured request whether each rule's text reached the model whole, in part, only through a later file read, or not at all. It reads the agent's repository through a fresh git directory that holds only the repository's data and none of its git settings, hooks or attributes, so nothing in that repository can run a program on the grading machine. A repository it can't read that way grades every rule unscorable with its own code: `REPO_NOT_GIT` (no .git), `REPO_LINKED_WORKTREE` (.git is a file), `REPO_REFTABLE` or `REPO_SHA256`.
- `collect.ts`: turns Harbor trial directories into the rows `analyze.ts` reads. A trial that stopped on an infrastructure error scores no rule. An agent timeout keeps its grades, but a rule whose trigger never fired before the timeout counts as not applicable. Every scored row, timeouts included, must show at least one captured request to the cell's model. Another model is allowed only when the trial's own harness settings (`agent/harness_settings.json`, `housekeeping_model`) name it as the harness's shipped housekeeping model; those calls are metered and listed on the row as housekeeping, never as the model under test. An agent timeout with no request to the cell model, whose capture is missing or parses cleanly and names nothing but housekeeping models, scores no rule (infra `TIMEOUT_NO_CAPTURE`). A scored trial in which no request to the cell's model got a successful answer in the proxy ledger scores no rule (infra `no_model_response`), even when a housekeeping call was answered. A QM trial on an arm that sets organization instructions (every QM arm but `none` and `qm-repo`) scores no rule (infra `QM_SOUL_NOT_DELIVERED`) unless the system prompt of its first agent-loop request starts the "## Organization instructions" section with that text, timeouts included. That check runs after the model checks, so a wrong model or an unreadable capture still stops the collection. A tool call that names this repository or its public copy marks the trial contaminated. Anything else stops the collection: a wrong model, a capture that doesn't parse, a capture cut at the proxy's size cap, or a trial whose captured housekeeping requests outnumber its requests to the cell's model. A Harbor job whose trial never started scores no rule, with the HE- code on its Harbor log's last error line as its infra code; a job with no such line also stops the collection.
- `analyze.ts` and `sequential.ts`: the analysis of the collected rows and the planned sequence of looks. A row outside the plan (a task not in the order, or a second-half row of a cell the interim look stopped) labels the analysis "invalid", and the command exits 1.
- `probe/`: a keyless tool anyone can run to see what their own agent sends from their own rules file.
- `plan.ts`: splits a run into shards, one setup each, with every arm on the design's task order. Filters cover the pilot (`--pilot`), a task subset, a list of arms and the two halves of the interim look. `--interim` plans the second half from `analyze.ts --look interim` output and refuses a look that is not complete, was taken on other tasks than this order's first half, or has no first-half rows for a setup being planned. It also writes one Harbor job per trial on the shard's machine, and on QM it refuses an arm whose organization instructions file fails the wiring's checks before any trial runs. Its `--smoke` job uses the first arm that is not `none`, and on QM not `qm-repo` either, so the QM smoke sets organization instructions.
- `run-shard.sh`: runs one shard. It stamps the task files, on a QM shard builds QM's images and pulls its Postgres image before any lease (exit 3 if that fails), checks the tasks (`task-preflight.ts`), copies them into Harbor tasks (`harbor-tasks.ts`), starts the metering proxy, runs the trials and turns them into rows with `collect.ts`. On a QM shard it removes leftover QM containers when it exits, after it has stopped the metering proxy and broker, and each docker call there has a time limit, so a stalled Docker daemon cannot keep the proxy running. On Ubicloud it runs under [`ubicloud/fanout.sh`](ubicloud/README.md), which adds this workload to the shared lane without editing it.

Rebuild and check: `bun scripts/rules-at-scale/corpus/build-corpus.ts build --check`, then `bun test tests/rules-at-scale-*.test.ts`.
