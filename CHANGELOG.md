## [0.0.13] - 2026-10-27

### internal-task: the fake adapter stops within seconds of SIGTERM however the signal lands

- `harnesses/_fake/adapter.sh`: the serve loop's TERM and INT trap now also sends TERM to the turn that is running (`tpid`, kept at serve scope and cleared after every turn). Before, a SIGTERM that landed after the post-spawn recheck and before `wait` started left `wait` sitting through the whole turn, which the Ubicloud check lane saw as "serve did not stop within 5 s of SIGTERM" under full-suite load (4 of 12 loaded conformance runs on main; 0 of 40 single-test and 0 of 12 full runs on this change under the same load).
- `tests/adapter-conformance.test.ts`: the SIGTERM test's wait for the first turn log line treats a missing `adapter.log` as "not yet" instead of throwing (the ready file is written one line before the adapter's first log line). A new test stops an idle serve before any turn ran, which fails if `tpid` goes back to loop scope (`set -u` ends the trap) or loses its empty-pid guard.

### internal-task: the lane's orphaned check VMs cost at most an hour once its watcher runs

- `scripts/ubicloud/pr-check.sh` names its VM `ubirun-<owner>-<epoch>-pr<n>` with the owner id `ubi-runner.sh owner` derives (so `list --mine` and `gc` see it whatever `UBI_OWNER` holds), before it posts the pending status. `scripts/ubicloud/pr-watch.sh --reap-after MINUTES` (60; 0 disables; a value that is not whole minutes exits 2) destroys this owner's check VMs older than that before each cycle, keeps a VM whose controlling process is alive on the watcher's machine (state written before the machine last booted counts as dead), leaves shard VMs alone, says so when the runner is missing or the list fails (with ubi-runner's reason), repeats ubi-runner's lines in its log as the receipt, waits at most `UBI_DOWN_TIMEOUT` (120 s) per VM and says `would destroy` under `--dry-run`; `UBI_RUNNER` overrides the runner as it does for `pr-check.sh`. Why: a `pr-check.sh` whose controlling machine sleeps posts no verdict and destroys nothing; on 2026-10-26 #85's check from another thread's machine left its VM up 51 minutes and #84's check from the lane machine, which restarted, left its VM up 3 h 17 min. The cap holds for VMs carrying the lane's owner while the lane's watcher is running; a VM another thread started is never swept, which is why `docs/ubicloud.md` (Limits) says the check lane runs from internal-task's lane machine only and what to do after a sleep. An inherited `UBI_DOWN_TIMEOUT` must be whole seconds from 1 to 999999 with no leading zero (ubi-runner's arithmetic reads a leading zero as octal and a unit suffix as an error, which would make every destroy fail), or the watcher exits 2 while the sweep is on; a state file whose pid is not a positive integer, a state file that cannot be read and a reboot that reused the controller's pid all count the controller as gone rather than ending the watcher or keeping the VM, and a VM name whose epoch has a leading zero is read as decimal rather than ending the watcher; `pr-check.sh` stops before the pending status when the owner lookup fails. The ship reviews of #86 found these and the sweep's failure line being swallowed by its own read loop, an owner slug that diverged from ubi-runner's for an empty or digit-leading `UBI_OWNER`, and a `--help` that had stopped printing the Needs paragraph; the sweep has 15 tests, from the destroy and keep paths to the default state root and `--help`.
