# Amendments: fable-5-2-coding-2026-11

## Amendment 1 (2026-11-09, before any trial result was read)

Written after a one-round plan review, while the canary shard fable52-r1h1 was booting from the preregistration commit `dba44ba4ff` and before any of its trials had a result. The other 11 shards run from this amendment's commit. Nothing here changes a task, a setting, a lease or the trial count; it fixes the analysis rules before any data exists.

- **Rate limits (clarified).** A trial that stopped with an error after an upstream 429 is `infra_error` with class `rate_limited` (scripts/frontier-harbor/to-trials.ts, unchanged), so it is excluded, pairwise as every exclusion is, and counted per arm. A trial that recovered from a 429 is scored as it ended, and its 429s are counted. Fable 5.2 launched today, so the report states each arm's rate_limited count. If more than 10% of any arm's trials are rate_limited, the report says that arm's result is incomplete and gives a line with those trials scored as fails.
- **Provider refusals (restated).** A refusal (for example Claude Code's AgentSafetyRefusalError) counts as a fail, as preregistered. Refusals are counted per arm with scripts/frontier-harbor/refusals.ts, and a line without refused trials is reported beside the headline.
- **Unfinished trials at the time stop.** A trial with no record at 22:45 UTC is reported as incomplete per arm and is not scored. Because the canary started early, unfinished trials could differ by arm. So beside the primary (tasks with at least one scored attempt in both arms), the report gives a sensitivity line on tasks with both attempts scored in both arms.
- **Cost per solved task is co-primary for Fable 5.2 vs Opus 5.5.** Opus's ceiling (about 12 points of room) is below the 14-point MDD, so a pass-rate win over Opus is unlikely to be measurable on this set. The paired cost-per-solve ratio, Fable 5.2 over Opus 5.5, with its 95% interval, is therefore reported as co-primary for that pair. A descriptive non-inferiority line is added: Fable 5.2 is "within 10 points of Opus" when the one-sided 95% lower bound of its difference is above -10 points.
- **Ceiling-raise (R61), named in advance.** If the Opus comparison is null because Opus is at the ceiling, the verdict is FIX-METHOD and the ceiling-raise is a harder test-scored set with headroom for Opus (for example DeepSWE run offline, or the held-out tasks), not run in this flash eval.
- **Analysis script.** `scripts/frontier-harbor/compare-models.ts` is committed here, before any trial result, and is the analysis the report uses. Its dry run on frontier-harness-2026-11's Claude Code trials reproduces that report's Opus 5.5 (88.5%, $0.63 per solve) and Fable 5.1 (71.2%, $2.86 per solve) numbers. It refuses any cell name outside the 12 preregistered cells.
- **Fable 5.2 request check (canary).** Claude Code 2.1.312 predates Fable 5.2, and the keyless install check does not run that model. So before the other 11 shards start, the canary's first Fable 5.2 trial's captured agent-loop requests are read for `output_config.effort: high`, adaptive thinking and max_tokens. If any differs from the Fable 5.1 and Opus 5.5 cells, nothing else starts, and a dated amendment decides.
- **Housekeeping.** The preregistration commit included a stray `__pycache__` file. It is removed here, and `__pycache__/` is added to .gitignore. Price sources: the Fable 5.2 rates were read from platform.claude.com/docs/en/about-claude/pricing on 2026-11-09 ($8 input, $10 five-minute cache write, $0.20 cache hit, $40 output per million tokens), and the limits from platform.claude.com/docs/en/models/fable-5-2/overview (1M context, 128K max output).
- **Quota.** Ubicloud showed 196 vCPUs in use by other owners before launch, and the project maximum is not readable. A shard refused for quota is queued again by fanout.sh, and any shard that starts late is named in the report.
- **One pull request.** The preregistration and the results share one pull request at the Captain's instruction for this run (internal-task, 2026-11-09), not by R77, which keeps two PRs. The registry entry's reason is corrected to say so. If the order check or CI refuses the shared PR, the Captain's fallback is two PRs, the preregistration landed first.
- **Erratum (2026-11-09, 22:56 UTC):** the Captain then split the preregistration into its own pull request, which lands before the results. The registry entry no longer declares `preregistered_on_main: false`, and it registers each of the four Harbor plan files as its own experiment, with its shards' results under it.

## Amendment 2 (2026-11-09, 21:10 UTC, before the other 11 shards ran any trial)

- **Canary request check: passed.** The canary's Fable 5.2 trial on chess-best-move sent `output_config.effort: high`, adaptive thinking and max_tokens 128,000 on every agent-loop request (3 of 3 captured requests), the same settings as the Fable 5.1 and Opus 5.5 cells. Amendment 1's condition is met.
- **No per-VM smoke on the other 11 shards.** The canary's keyless install check took 24 minutes (20:07 to 20:31 UTC). Repeating it on each VM would leave too little time before the time stop. So the other 11 shards run with `--no-smoke`. They run the same run code the canary's check passed: amendment 1's commit changed only documents, the analysis script and .gitignore.
- **Later start than planned.** The other 11 shards launched at about 21:08 UTC, about 37 minutes after the canary's first trial started, not 15 to 20 minutes. So the canary (Fable 5.2, attempt 1, first half) is further ahead than planned. The 22:45 UTC time stop is unchanged. A large share of trials will be unfinished at the stop, and each arm's unfinished count is reported.
- **Mid-run pulls.** Claude Code's session folders inside each trial are not readable by the pull's user, so the mid-run pull to the controller fails. A loop on the controller makes the job folders readable on each VM (chmod a+rX) every few minutes so results leave the VMs during the run. Nothing on a VM that a trial reads is changed.
