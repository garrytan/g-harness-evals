# Sealed custody of held-out sets

From v0.3, a held-out set's task bodies, hidden facts, world slice and corpus pages never enter main until the set retires. Main holds digests (commitments), the openings ledger and, after each opening, an allowlisted export. The plaintext lives only in an age-encrypted bundle on the orphan branch `custody` of this repository (`refs/heads/custody`, never merged into main), and only the custody scripts read the key that opens it. This page is the protocol; the code is `scripts/sealed/`, `runner/heldout/sealed.ts` and the `--sealed-root` flags of the runner and shard scripts. It does not change v0.1 or v0.2, which stay plaintext with their digests and are spent ([methodology](methodology.md), item 13).

Why: a held-out set measures generalization only while nobody who shapes a candidate has seen it. With bodies in main, every reader (people, agents, and any model trained on the repository) has seen them. Sealing makes "nobody has seen it" checkable up to the custody scripts, and the openings ledger plus the custody access log make "how many times was it looked at through the scripts" checkable.

Every sealed result is labelled **procedural custody**: the cryptography keeps the plaintext out of main and out of every terminal, but who may run the scripts is a rule the crew follows, not a lock (below, "What remains procedural").

## Roles

| Role | Who | Reads the key | Reads raw sealed receipts |
|---|---|---|---|
| Custody scripts | `scripts/sealed/*`, run by the custodian thread | yes: the drive copy, after checking the escrow; never printed | yes, inside custody only |
| Custodian | one agent thread named by the coordinating agent for a set; it runs the scripts and reads only what they print | no; it never opens the identity file | no |
| Set author | writes a set's plaintext outside any checkout and seals it with the public recipient | no | no; after sealing, the author deletes the plaintext and does not author or tune candidates measured on that set |
| Adapter, preamble and loop authors; gbrain threads; every other agent thread | everyone else | never | never; they read the public export, the decision bits and, after release, the released receipts |

Who needs a human: nobody. The identity was generated by `scripts/sealed/keygen.ts` in-process, written to the project-user drive and escrowed on the custody branch; no person handles a key, an environment variable or a project setting.

## Where things live

- Main: `sealed/recipient.txt` (the public age recipient), `sealed/backups.json` (the sha256 of the backup each set was sealed from, below in "Status, replacement and backup records"), `tasks/multiuser/<set>/heldout/MANIFEST.json` with `"custody": "sealed"`, empty `tasks` and `files`, the `tree_sha256`, the openings ledger, and a `sealed` block (`bundle_sha256`, `world_slice_sha256`, `heldout_corpus_sha256`, `task_count`, `recipient`, `custody_repo`, `custody_ref` (always `refs/heads/custody`), `bundle`, `sealed_at`, and `extras`, the bundle path and sha256 of each `--include` file, when there is one). Nothing else of the set is in the tree; `bun scripts/seal-heldout.ts --check` (CI, keyless) fails if anything is. Each opening's export goes to `docs/benchmarks/<run>/sealed-results/`.
- The custody branch (`refs/heads/custody` of garrytan/harness-evals, an orphan branch with no history in common with main): `README.md`, `escrow/identity.age` (the identity encrypted under a passphrase derived from `UBICLOUD_API_KEY`), `<set>/bundle.tar.age`, the encrypted raw results of each opening at `<set>/results/<run_id>.tar.age`, and `access-log.jsonl`, one line per custody event (`sealed`, `opened`, `resumed`, `exported`, `released`, `escrowed`, `reencrypted`, `compared`). Every write is one commit pushed by its sha to `refs/heads/custody` without force after `scripts/sealed/custody.ts` validates that commit: only new age ciphertext to an X25519 recipient at those paths, a replaced escrow that is age scrypt ciphertext, and schema-checked appends to the access log; nothing deleted or rewritten, and no age identity anywhere.
- The custody clone: every custody command works in an isolated clone whose HEAD is `refs/heads/custody` (`--custody`, default `~/.capy/work/custody/harness-evals`, made from the checkout's remote when missing). The scripts refuse the public checkout, a directory inside it, or a worktree of it as the custody clone, and keep the two refs apart in every command: the public ref (`origin/main`) for the preregistration and the ledger, the custody ref for ciphertext and the log. The opening receipt records both (`public_ref`, `public_commit`, `access.custody_ref`, `access.custody_commit`). Every custody transaction, and every sync of the clone, holds the clone's lock (a `custody.lock` directory in its git directory, holding the owner's pid), so processes sharing the default clone take turns; a waiter gives up after 10 minutes with HE-SEALED-011, and a lock whose process has died is taken over. Before every fetch and push the scripts check each URL the remote resolves to (its fetch and push URLs, or a `--remote` URL and any insteadOf or pushInsteadOf rewrite of it): only a `file://` URL or an existing local directory counts as local, and every other URL, scp form included, must name garrytan/harness-evals as its whole path on github.com or git.capy.ai, any port (HE-SEALED-013). Every other host is refused. That includes open.ts's fetch of main into the public checkout. Every custody fetch, ls-remote and push also runs with `GIT_ALLOW_PROTOCOL=https:ssh:file`, which git treats as `protocol.allow=never` with only https, ssh and local files allowed and which overrides every `protocol.*` setting, so no remote helper (`ext::`, `fd::`, `<name>::`) runs whatever a git config says.
- The identity: one age X25519 identity in a file in the project-user drive, read only by `scripts/sealed/*`. Its path is `--identity`, else `HE_CUSTODY_IDENTITY`, else `custody_identity` in `config/local-paths.json` (private checkout only; the public export leaves that file out). The drive's FUSE mount reports mode 0644 whatever was requested, so no check depends on the file's mode.
- Opened root (custodian's machine only, never inside a git work tree, default `~/.capy/work/sealed/<run_id>`): `opening-receipt.json`, `tasks/multiuser/<set>/heldout/<task>/`, `world/slice.json`, `world/world.json` (the public world with the slice merged in), `corpus/heldout/<slug>.md` (a slug can start with a category directory, so pages may sit at `heldout/<category>/<page>.md`), `extras/<path>` for each `--include` file, `opaque-salt` (below), and `logs/` for the custody commands that log there. Files are written 0600.

## Lifecycle

1. **Seal.** The set author writes the plaintext tree, a world slice and its corpus pages (the messy-company `heldout/<slug>.md` pages its held-out brains index) outside every checkout. The slice is in world.json format, the format of `world/seed/world.json`: either the whole world, whose world_id, today, time_zone, source and non-held-out records must be exactly the public world's, or only its held-out records (split `heldout`), which replace every public held-out record. The author then runs `bun scripts/sealed/seal.ts --task-set <set> --tasks <dir> --slice <slice.json> --corpus <dir>`. It refuses a repository that is not private, a set named `v0.1`, `runner`, `tasks` or `docs` (a custody clone holding one of those trees is refused, so such a bundle would lock out every custody command), inputs inside the checkout, a symbolic link in the tasks or corpus input (a linked page would be packed but left out of the corpus digest), a `--corpus` with no page, plaintext of the set in the checkout, slice ids of records the public world keeps, held-out slice records that copy a public held-out record unchanged, in any key order (a slice may reuse a public held-out id, since every public held-out record is replaced, but not its content), a set with an opened row, and a bundle already on the custody branch. It pushes the bundle to the custody branch with a `sealed` line and writes the manifest; the author commits the manifest in a pull request to main, then deletes the plaintext.

   **Sealing from an author's encrypted backup.** An author may hand the custodian a backup of their working tree instead of plaintext: a tar (plain or gzipped) encrypted to `sealed/recipient.txt`. The custodian thread runs `bun scripts/sealed/seal.ts --from-backup <file.tar.age> --sha256 <hex> --task-set <set> --tasks <path> --slice <path> --corpus <path> [--include <path> ...] [--exposures <file.json>] --custodian <thread code>`. Here `--tasks`, `--slice`, `--corpus` and `--include` are paths inside the backup. For v0.3: `--tasks v03/selected/tasks --slice v03/world/slice.json --corpus v03/corpus-seal --include v03/selected/exclusions.json`.
   - **Digest first.** `--sha256` is required with `--from-backup`: the custodian passes the digest the author sent. A run without it, or with a value that is not 64 hex characters, is a usage error (HE-RUN-002) before anything is read or decrypted. A backup with another digest is refused (HE-SEALED-006) before anything is decrypted. seal.ts refuses any flag it does not know, so a misspelled `--sha256` is an error, not a skipped check, and any flag but `--include` given twice.
   - **Key through the escrow check.** The identity comes only from `custodyIdentity`, after the escrow check, as for open.ts. It is never printed, logged or put in argv.
   - **Unpacked outside every checkout.** The backup is decrypted in memory and parsed whole, and only the entries under the named paths are written, into a fresh 0700 directory under `~/.capy/work/custody/intake/`, refused inside a git work tree, under the Capy drive or through a symbolic link. The 0700 mode does not protect against other threads on the same machine, which share the user. Unpacking refuses absolute paths, `..`, symbolic and hard links, devices, fifos and sparse files, and follows no link. A link anywhere in the backup, residue included, refuses it: the author makes a new backup without it. A `./` root entry (from `tar -cf backup.tar .`) is accepted.
   - **Only the named inputs are sealed.** The ordinary seal runs on the named paths, with every refusal above. Residue beside them (candidates, audits, proxy logs, caches, logs) never enters the bundle. Corpus pages one level down (`heldout/<category>/<page>.md`) are packed and counted in `heldout_corpus_sha256` like any page.
   - **Extras.** Each `--include` file is packed at `extras/<path>`, covered by the bundle digest and listed with its sha256 under `sealed.extras`. open.ts writes it to `<root>/extras/<path>` and release.ts to `tasks/multiuser/<set>/sealed-world/extras/<path>`, each after checking the digest. Their text is sealed text: guarded output redacts it and the export leak scan flags it, including short ids under JSON `id` keys. The opening receipt records the extras and `verifySealedRoot` checks them, so a missing or edited extra fails the root before a run or export.
   - **Exposures.** `--exposures` adds a JSON list of exposures (`date`, `kind`, `recipient`, `what`, `source`) to the manifest's openings ledger: for example the generator and auditor models, the proxy logs, the response caches and the author. If the manifest has no ledger yet, add `opening_budget`, `alpha_per_opening`, `status` and `openings` before committing it.
   - **Custodian.** `--custodian` names the custodian in the access log's `sealed` line (default `scripts/sealed/seal.ts`), as `open.ts --custodian` does.
   - **The plaintext goes.** The intake directory is removed on success, refusal, error, SIGINT, SIGTERM and SIGHUP, and seal.ts prints one line saying it is gone. A SIGKILL or a machine stop leaves it: the next seal.ts run and every cleanup.ts run remove stale intake directories (`bun scripts/sealed/cleanup.ts --intake` does only that). A directory is stale when no process with the pid in its name runs, or the one that does has other start ticks than the name records (a pid reused after a restart). Ordinary seal.ts runs sweep too.
   - **Output.** A refusal prints its code, a problem count and a private log path, as for any seal.
2. **Preregister.** As for any held-out run: a `heldout` block in `prereg.json` (set, label, reason for dev, `candidate_sha256`, and the claims export.ts decides) and a `planned` ledger row, in a preregistration pull request merged before the opening. CI, open.ts (before the opening is pushed) and export.ts all refuse claims export.ts could not decide, so a bad claim never spends an opening.
3. **Open.** The custodian runs `bun scripts/sealed/open.ts --prereg docs/benchmarks/<run>/prereg.json`. Before anything is decrypted it requires the repository to be private, a clean public checkout at `origin/main` (re-running the ledger check there), the bundle on the custody ref with the committed digest, and the escrow check (`keygen.ts --check-escrow`, below) against `sealed/recipient.txt`, which must be the recipient the set was sealed to. It then decides admission and pushes the `opened` line with compare-and-push. Each admission attempt fetches main again, requires the checkout to still be clean and at `origin/main` with the preregistration, the set's whole sealed block and `sealed/recipient.txt` unchanged, and reruns the ledger check there, so a withdrawal, amendment or order change that landed meanwhile is seen; the access log on the custody ref decides what was already opened. A rejected push refetches the custody ref and reruns the whole admission, so two custodians can never both take the last opening, and a push that keeps failing ends the open before decryption. open.ts always reads main (it has no `--branch`); the two refs cannot move in one transaction, so a main change landing after the push that admitted the opening is not seen by it. It then decrypts, merges the world, verifies every digest and writes `opening-receipt.json`, which binds the run id, preregistration digest, candidate, label, both refs and every commitment. Running it again for the same run is an idempotent resume (a `resumed` line); a changed candidate under the same run id is refused. A set whose access log has a `released` line takes no opening or resume.
4. **Build and run.** `bash scripts/build-gbrain-image.sh --sealed-root <root>` builds the brains from the root's `world/world.json` (the public world with the slice's held-out records in place of the public ones) and the root's `corpus/heldout/` pages in place of the public held-out pages, through the same route as a public build: gbrain/Dockerfile's `world-input` and `heldout-corpus` stages feed `gbrain/build-brain.ts`, which stages the pages and loads them with `gbrain import`, and the image records `world_sha256` and `heldout_corpus_sha256` in `/opt/sidecar/image.json`; `runner/run.ts` refuses an image whose digests differ from the receipt (HE-SEALED-005), defaults a sealed run's gbrain cells to `harness-eval/gbrain:sealed-<run_id>` when `--gbrain-image` is not given, and refuses a run with no sealed root an image built from one (image.json `sealed: true` or a held-out corpus digest, or the label `harness-eval.sealed=true` when image.json has no `sealed` field; HE-SEALED-005). `plan`, `dry-run`, `preflight` and `run` take `--sealed-root <root> --opening-receipt <root>/opening-receipt.json`, and `run` refuses `--harness-mode process` for every non-scripted cell of a sealed run before it opens the root (HE-SEALED-001), since a process-mode harness runs as the runner's user and could read the root whichever cell it serves; plan copies the receipt into the manifest and every later step refuses a receipt of any other opening (a receipt rewritten by resuming the same opening is accepted) or a root whose contents changed. `scripts/run-shard.sh` works on its own private copy of the root (a `mktemp -d` directory under `TMPDIR`, mode 0700, refused inside a git work tree, as is an `--out` inside any git work tree (HE-SEALED-002), before anything is written; each launch appends the copy's directory to `<out>/sealed-root-copy.path` so cleanup.ts can remove a copy a SIGKILL or machine stop left; a failed copy prints only the path of `<out>/sealed-root-copy.log`, which holds cp's diagnostics), which plan, preflight, run and the image build read and which is removed on every exit bash can trap (success, failure, INT and TERM), so the custodian's root is never written by a shard and stays for export; the copy's `logs/` (the sealed image build log) is kept at `<out>/sealed-root-logs/` first. Shards on Ubicloud pass both through `scripts/ubicloud/fanout.sh`; `scripts/ubicloud/run-shard.sh` copies the root to the shard's VM, re-copies it on `--resume`, and deletes it on every exit with the VM; a sealed lane's one-trial smoke runs as a public dev run, without the sealed flags and on the public `harness-eval/gbrain:dev` image, and the counted shard then builds the receipt-bound sealed image; a sealed `--attach` whose `--dest` is inside a git work tree is refused before it polls or pulls; tar and unpack diagnostics of those uploads go to `<dest>/sealed-upload.log` only (never the lane log; cleanup.ts removes it), and a failed upload prints a fixed line naming that file. The identity never goes to a VM. Raw results stay outside every checkout. A sealed build is tagged `harness-eval/gbrain:sealed-<run_id>`, never the public `harness-eval/gbrain:dev` (build-gbrain-image.sh refuses it, and `scripts/run-shard.sh` passes the sealed tag to preflight and run), so a plaintext run on the same machine never reads the sealed brains.
5. **Merge, summarize and compare inside custody.** `scripts/merge-shards.ts`, `scripts/summarize-run.ts` and `scripts/compare-run.ts` need `--sealed-root` for a sealed run (HE-SEALED-001), so families come from the sealed task tree and never fall back to "unknown" (a plaintext run still counts a task with no readable task.toml as "unknown", with one WARN line and `families_unresolved` in summary.json). Under a sealed root they print one line naming the files they wrote; their tables go to log files in the raw results. `merge-shards.ts` prints its merged counts and shard table, and a refusal (which names trial ids) goes to `<out>/merge-shards.sealed.log`. Before that log is created it refuses a mix of sealed and plaintext shards (HE-SEALED-001), an `--out`, `--sealed-root` or shard directory inside a git work tree (HE-SEALED-002), and a root whose `opening-receipt.json` is missing or is another opening than the shards' manifests (HE-SEALED-003); shards planned from a receipt rewritten by resuming the same opening merge.
6. **Export.** `bun scripts/sealed/export.ts --results <raw dir> --sealed-root <root> --opening-receipt <file>` refuses a repository that is not private; refuses (HE-SEALED-007, nothing pushed or published) when the set's `sealed.recipient` is not the checkout's `sealed/recipient.txt`, when the access log has a `released` line for the set, or when the receipt's `access.event_sha256` is missing or not the digest of the run's first `opened` line, or the run has no `opened` line (the last two checked after each custody sync and again inside the push transaction); makes every claim source again from the current `trials.jsonl` with `compare-run.ts` (the preregistered defaults, plus one `--margin` per noninferiority claim; the sources are `comparisons.json` and `comparisons.gbrain.json`, and any other claim source is refused), overwriting any comparisons file already in the raw results rather than reading it; stages the public export (below) in `<results>/export-pending/<sha256 of the bundle>/` (mode 0700, outside every git tree, left out of the bundle), pushes the gzipped, encrypted raw results to the custody branch with an `exported` line, then copies the staged files into the run's `sealed-results/` directory (opening-receipt.json and README.md first and export.json last, each through a temporary name) and prints the next step. A raw results bundle over 95 MiB (GitHub refuses a pushed file over 100 MiB) is refused before anything is written. The bundle leaves out harness state and workspaces under `trials/` and the compiled gbrain in each Claude Code or Codex installer view (`gbrain-install/<harness>-installer/<split>/home/.local/bin/gbrain`, and the same under each `<shard>.gbrain-install/`): about 67 MiB gzipped per copy, so two copies alone would pass the limit (issue #192). The view's `manifest.json`, which stays in the bundle, records the binary's sha256. The binary is left out only when its manifest entry has `source_path` `<harness>/installer/home/.local/bin/gbrain`, the binary matches that entry's sha256, the manifest's `view_digest` is the digest of its own file list (the adapters' check), and a trial in `trials.jsonl` recorded that `view_digest` for the harness and split (`gbrain.install_bundle.view_digest`). A binary with no such entry or another sha256, or a manifest whose `view_digest` does not match its file list, is refused (HE-SEALED-007) and nothing is written. A consistent view that no trial recorded (every trial of the cell ended before the view was mounted) keeps its binary in the bundle, under the same 95 MiB limit. So after release, `verifyInstallView` on a view whose binary was left out reports `home/.local/bin/gbrain` missing by design. The manifest's sha256 and `gbrain_commit` name the binary, but its bytes come back only from the run's gbrain image while that image is kept (`cleanup.ts --images` removes it), because nothing shows the gbrain build is byte-reproducible. A run already exported is never exported again: when custody holds its bundle and `exported` line and the staged `export.json` names that bundle's digest, a rerun finishes an export whose write into `sealed-results/` did not complete (a crash or a failed write after the push) by copying the staged files; when `sealed-results/` already holds them it refuses, saying the export is complete; otherwise it refuses and names what is missing. The custodian commits `sealed-results/` in a results pull request.
7. **After the export.** `bun scripts/sealed/cleanup.ts --export docs/benchmarks/<run>/sealed-results/export.json --sealed-root <root> --results <raw dir> [--results <each shard and merged results dir>] [--images]` first checks that `--export` is the run's complete public export in the checkout (README.md and the receipt export.json names beside it; export.ts copies export.json last, so a partial copy is refused), then proves the encrypted copy (the raw results bundle on the custody ref has the export's digest and the access log has its `exported` line; otherwise nothing is removed), then checks that the three public files are committed as they stand and that the commit holding them is on a remote-tracking branch (the results' export-pending/ copy goes with the cleanup, so an unpushed export would have no other copy), then removes every plaintext copy: the opened root, the shard and merged raw results with the custody logs inside them (each `--results` directory must name this run: every run id it carries, from manifest.json, the first trial_id of trials.jsonl, shard.json or shard-vm.json, must be the export's and at least one must be readable, or nothing is removed), for a Ubicloud lane's `<dest>/results` the plaintext copies beside it (`run-shard.log`, `run.stdout.log`, `run.log`, `vm-shard.out`, `sealed-upload.log` and `smoke/`; `shard-vm.json`, `lane.log` and `cleanup-pending` stay), any sealed shard root copy a killed `scripts/run-shard.sh` left, named by a `sealed-root-copy.path` line, when it exists on this machine as a `harness-eval-sealed-shard.*` directory outside every git work tree holding this run's opening receipt (`scripts/run-shard.sh` copies it into the directory before the root, so a copy killed partway is still bound to its run; a listed copy that no readable receipt binds to a run is printed as unresolved and cleanup exits 3), and with `--images` every local docker image labelled `harness-eval.sealed=true` plus the docker build cache that holds the sealed build contexts. A Ubicloud shard's `shard-vm.json` records `cleanup: "done"` and `destroyed_at` only after `ubi-runner.sh down` succeeded; a failed down keeps the VM id in `<dest>/cleanup-pending`, and a controller that crashed leaves `cleanup: "pending"`. cleanup.ts prints any such VM id as unresolved cleanup and exits 3, so the sweep (`bash scripts/ubicloud/ubi-runner.sh list --mine`, then `down <vm>`) is not forgotten. Every cleanup.ts run also removes stale seal.ts intake directories, and exits 3 when one cannot be removed.
8. **Retire and release.** A set replaced by a reseal is the exception: it waits for the new set (see "Re-encrypting for regeneration" below). When the set retires (budget spent, or a decision to stop), `bun scripts/sealed/release.ts --task-set <set> --retire` refuses while the access log has an `opened` line for a run of the set with no `exported` line (a released set takes no export, so that run would never get a decision or an encrypted copy of its raw results; finish or export that run first, and an abandoned opening blocks release until the owners decide how to record it), and while it has an `exported` line for a run of the set with no `sealed-results/export.json` (finish that export first; a rerun of export.ts completes it from its staged files), checks the escrow, decrypts the bundle and every exported run's raw results from the custody ref, checks every digest the public files committed on the decrypted bytes in memory, refuses any destination that is a link or holds other bytes (an identical file is accepted), and only then writes the task tree, the slice, corpus and extras (`tasks/multiuser/<set>/sealed-world/`, extras under `sealed-world/extras/`) and each run's receipts (`docs/benchmarks/<run>/results/`), and rewrites the manifest as a plaintext manifest with status `retired`, keeping the commitments under `released`. Every refusal but one comes before the first write, so the public checkout is unchanged. The exception: the `released` push reads the access log again and refuses, leaving the manifest sealed, when an `opened` line for a run with no `exported` line, or an `exported` line for a run release did not verify, landed meanwhile. Each file is written beside its destination and renamed into place, so a failed write leaves no truncated file; a failed `released` push comes after the writes and leaves the manifest sealed, and a rerun finishes the release. The custodian opens the release pull request; the full per-task numbers can then be written from the released receipts.

## Re-encrypting for regeneration

**An author who must regenerate a set gets their own backup back, encrypted to their own key.** The custodian never hands over plaintext, and the author never gets the custody key. The custodian then compares the new backup with the old one by task family, world-slice record and corpus page. Neither step is an opening, and neither writes plaintext to disk. The v0.3 to v0.3-gen6 check is recorded in sealed-records/v0.3-gen6-reseal.md.

When: a set was sealed from an author's backup, part of it has to be redone, and the set has never been opened (for v0.3, the coordinating agent's decision of 2026-10-30, option A). Both scripts refuse a set with an `opened` run, a set with a `released` line, a set whose `<set>/bundle.tar.age` is not on the custody branch, a set whose world slice or corpus a live sealed set shares (a backup of it holds that set's content; name that set with `--set`), a set whose `replaced_by` chain names a set still in sealed custody and not retired as a replaced set, and every set while another set's `MANIFEST.json` does not parse or validate (below, "Status, replacement and backup records"). They check before decrypting and again under the custody lock, just before the push.

**Step 1, rekey.** The author sends an age X25519 recipient of their own (`age1...`, from `age-keygen`). The custodian runs:

```
bun scripts/sealed/rekey.ts --from-backup <file.tar.age> --sha256 <hex> --to <author's age1 recipient> --out <path> --set <set> [--declare-backup <hex>] --custodian <thread code>
```

- **Same checks as `seal.ts --from-backup`, in the same order.**
  1. `--sha256` (required, 64 hex characters).
  2. `--to` must parse as an age X25519 recipient (the age library's own parser) and must not be the custody recipient.
  3. `--out` must not exist and must be outside every git work tree.
  4. The repository must be private.
  5. The backup's sha256 must match `--sha256`.
  6. The set state checks above.
  7. The backup must belong to `--set` (below, "Backup records").
  8. The key comes only from `custodyIdentity`, after the escrow check.
- **In memory only.** The backup is decrypted in memory. A backup the custody identity cannot open is a refusal naming `--from-backup`. The intake reader parses it, only to refuse an unsafe tar. The identical decrypted bytes (the same tar or tar.gz) are encrypted to `--to`.
- **Logged first, written second.** The `reencrypted` line is pushed while the new ciphertext is still only in memory. After the push, the ciphertext is written to a temporary name beside `--out`, fsynced and linked to `--out`, and the directory is fsynced. It never overwrites.
  - A refused push writes nothing.
  - If the write or the link fails after the push, the temporary file is removed and nothing is at `--out`. The refusal says the line was pushed. That line then records an exposure that never happened, which is the safe direction. Run again with a new `--out`.
- **The `reencrypted` line.** `run_id` `*`, the set, the custodian, `source_sha256` (the backup), `output_sha256` (the new file), `recipient` (`--to`) and, when `--declare-backup` bound the backup, `declared_sha256`. No other custody file changes.
- **Output.** One line: the two sha256 values and the custody commit. Send the file and its sha256 to the author.

**Step 2, compare.** The author regenerates and sends a new backup, encrypted to `sealed/recipient.txt` as before. The custodian runs:

```
bun scripts/sealed/compare-backups.ts --a <old.tar.age> --a-sha256 <hex> --b <new.tar.age> --b-sha256 <hex> --tasks v03/selected/tasks [--tasks <dir> ...] [--family-field] --allow-family <family> [--manifest <file in backup b> --manifest-commit <key>=<commit> ...] --slice v03/world/slice.json --corpus v03/corpus-seal [--allow-group <group> ...] [--allow-family-pages] --set <set> [--declare-backup <hex> ...] --custodian <thread code>
```

- **`--set` names the old, sealed set before the reseal, and the new set after it.** Before the reseal lands, `--a` is the old set's backup and `--b` the new one, which no file records yet, so `--b` needs `--declare-backup <its sha256>`. Once the new set is sealed and not retired, both scripts refuse the old set, since a backup of it holds the new set's content. Then `--set` names the new set: `--a` is the backup of the set it replaced and `--b` its own. For v0.3 that is gen5 against gen6 with `--set v0.3-gen6`. The regenerated backup is sealed under a new set name (for v0.3 the reseal is `v0.3-gen6`). The old seal is retired unopened. Its manifest's `status` becomes `retired`, it names the new set in `replaced_by`, and its `openings` stay empty.
- **The old set takes no opening and no release while the new one is live.** Its world slice, corpus and unchanged tasks are the new set's, so opening or releasing it would expose the new set. Both are refused while another set in sealed custody, not retired, has the same world slice or corpus digest (the digest of an empty corpus never counts), or while a set in the old set's `replaced_by` chain is in sealed custody and not retired as a replaced set, whatever its digests: `checkPlan` (so run.ts plan and open.ts) refuses a planned opening, dev or confirmatory, with HE-HELDOUT-003 (and the CI ledger check reports its planned row), and release.ts refuses with HE-SEALED-008 before decrypting, again before writing and again before it pushes the `released` line. `check-sealed-publication.ts` also refuses released files and raw receipts of such a set. Once the new set's retirement is on main and in the custodian's checkout, the old one can be released: release.ts, rekey.ts and compare-backups.ts read the manifests of the checkout and of main fetched fresh from the custody clone's remote (into a ref of the process, `refs/sealed/main-<pid>`, deleted afterwards), so a stale checkout, or one whose own remote is a fork, cannot hide the new set. That remote must have one URL for fetch and push, so main comes from the repository the custody branch is pushed to. A `url.<base>.insteadOf` rule in the checkout that would send that URL elsewhere is refused (HE-SEALED-013).
- **A reseal blocks release and regeneration from the moment its bundle is on the custody branch.** seal.ts pushes the bundle before the new set's manifest can reach main. Until that manifest is on main (or in the checkout), release.ts, rekey.ts and compare-backups.ts refuse every other set, because whether the new set shares its world slice or corpus is unknown. A manifest that does not commit to that bundle's sha256 counts as none: a malformed or empty one, JSON null, or one naming another bundle. Every custody push is compare-and-push and the check runs again in decide() under the custody lock, so a reseal that lands while a release decrypts makes the release's push retry, and the retry refuses.
- **Checks, in order.**
  1. Both digests are required, 64 hex characters, and different from each other.
  2. The repository must be private.
  3. Each backup's sha256 must match.
  4. The set state checks above.
  5. Both backups must belong to `--set` (below, "Backup records").
  6. The escrow check.
  7. Both backups are decrypted in memory. A backup the custody identity cannot open is a refusal naming `--a` or `--b`.
- **The `compared` line** lists `declared_sha256` when `--declare-backup` bound a backup.
- **What is compared.** A directory listed in the tar or implied by a path counts as a directory.
  - **Tasks:** each immediate subdirectory of `--tasks`. `--tasks` may repeat (`--tasks v03/selected/tasks --tasks v03/candidates`); with more than one, every family count is per directory. Its digest covers its directories (empty ones too), and its files' paths, executable bits and bytes. Its family is the name before the first `-` (`ix-01-foo` is family `ix`; a name with no prefix is `(none)`).
  - **`--family-field`:** the family is instead the top-level `family` string in the task's `task.toml`, as the v0.3 generator writes it (`approval_relay`). Use it when task ids are opaque and share one prefix. A task with no readable `family` is `(none)`. A task whose family differs between the two backups, or whose `task.toml` reads in one and not the other, is `(moved)`, which is never allowed.
  - **Manifest (`--manifest <file in backup b>` with `--manifest-commit <key>=<commit>`, optional, repeatable key):** the dotted JSON key (`proof.template_commit`) must hold 7 to 40 hex characters that abbreviate, as an object id in `--repo`, the same commit as `<commit>`; a branch or tag named like the value does not count. The value never prints, only the key, the full expected commit and `match` or `no match`. It shows what the author's manifest says; it cannot show the author really generated from that commit.
  - **Slice (`--slice`, optional):** record by record per collection (`teams`, `members`, `accounts`, `channels`, `messages`, `files`, `calendar`, `mail`), keyed by record id. The other top-level keys count as one item.
  - **Corpus (`--corpus`, optional):** page by page, bytes and executable bit. A differing page whose name starts with an allowed `<family>-` is counted apart from the others. The name is the author's choice, so such a page needs judgment unless `--allow-family-pages` is given.
  - **Everything else:** files directly in `--tasks`, directories, and every other file, by path, kind, executable bit and bytes. Grouped by the first two path segments (`v03/world`, `v03/audits`).
- **What prints.** Counts only (same, changed, added, removed) per family, group, slice collection and the corpus.
  - A family prints when it is 2 to 4 lowercase letters. Otherwise it prints as the first 12 hex characters of its sha256. With `--family-field`, a family prints by name when it is lowercase words joined by `_` and is the family of a `task.toml` committed under `tasks/` at `HEAD` in `--repo` (the public dev families; the index and uncommitted edits do not count) or an `--allow-family` value; any other prints as that digest. A `--tasks` directory prints in the report segment by segment, by the same rule as a group label: a segment a group label would hash prints as its digest. A refusal names `--tasks` as given.
  - A group prints one segment at a time. A segment prints as is only when all three hold:
    - it is lowercase words joined by `_` or `-`, or `v` and digits (no other digits, no uppercase);
    - compared case-insensitively, it contains no task id of either backup and no `<family>-` for a family of either backup or of `--allow-family` (with `--family-field`, also no `task.toml` family of either backup that prints as a digest, with `-` and `_` treated alike);
    - it is a directory wherever it exists, in both backups.

    Every other segment prints as the first 12 hex characters of its sha256.
  - It never prints a path below the second segment or any content. A task id prints only inside a digest.
  - The pass or judgment line names what was checked, including "no --slice" or "no --corpus" when those were not given.
- **Exit codes.**
  - **1:** a task outside `--allow-family` changed, was added or was removed, or a `--manifest-commit` key does not match.
  - **3, needs judgment:** every task check passed, but a non-task entry, a slice record or a corpus page differs outside `--allow-group`. Corpus pages named for an allowed family count as allowed only with `--allow-family-pages`, and the pass or judgment line gives their count either way. `--allow-group` takes a group as printed, raw or as its digest label, and covers the slice and corpus when their group is named. The custodian judges these before sealing the new backup.
  - **0:** only allowed things differ.
  - **2:** a refusal.
- **Comparing after the reseal.** Once the new set is sealed, the old set is refused, so a later compare of the old and new backups names the new set: `--set v0.3-gen6`. Its checks are the same, and its `compared` line is not an opening and spends no budget.
- **The `compared` line.** `run_id` `*`, the set, the custodian, `source_sha256` (`--a`) and `output_sha256` (`--b`), with no recipient. It is pushed before anything is printed, so a refused push prints nothing.

**Not an opening.** open.ts, export.ts, release.ts and the openings ledger count only `opened` lines, so a set with `reencrypted` and `compared` lines still has its full budget. `tests/sealed-rekey.test.ts` checks this.

**What stays procedural.** The author holds plaintext again while regenerating, outside every checkout, as when they first wrote the set. The new set's exposures list should say so.

## Status, replacement and backup records

**A sealed set's status only moves forward.** It goes `open` -> `spent` -> `retired`, or `open` -> `retired`. It never leaves `spent` or `retired`.

**A sealed set retires in one of two ways.**
- **Released.** `release.ts` writes a `released` block and turns the manifest plaintext.
- **Replaced.** The set stays in sealed custody with status `retired` and names the set that replaced it in `replaced_by`. For example, v0.3 has `"replaced_by": "v0.3-gen6"`.

**`replaced_by` keeps the old set protected.** A reseal can change the slice and keep the task bodies, so a digest match is not enough. While any set in the old set's `replaced_by` chain is in sealed custody and not retired as a replaced set, the old set takes no opening and no release, and its released files and raw receipts stay off main. This holds even when no slice or corpus digest matches. A chain that names a set with no manifest, or loops, counts as live too.

**A broken manifest fails closed.** A `MANIFEST.json` that does not parse, or that the guard cannot read (not an object, a `custody` other than `"sealed"`, no `sealed` block under `"custody": "sealed"`, a `sealed` block without `"custody": "sealed"`, a multi-user sealed set without both a slice and a corpus digest, a digest that is not a sha256, an unknown status, a `replaced_by` that is not a set name), never drops out of the checks. The guard counts it as a live sharer of every other set, and the publication check treats its set as still sealed. A set whose own manifest is broken takes no opening, release or rekey until it is fixed. Each refusal names the set and says why.

**`bun scripts/seal-heldout.ts --check` enforces this keyless.**
- `replaced_by` names another set that has a manifest, never loops, and sits only on a retired set.
- A set in sealed custody with status `retired` must have `replaced_by`. So hand-flipping a live set such as v0.3-gen6 to `retired` fails.
- Every set that the base branch holds in sealed custody is compared with its base manifest. The base is the merge base of HEAD with `origin/main` (or `main`), read with git, as the openings check finds it.
  - The status may only move forward.
  - The set leaves sealed custody only with the `released` block release.ts writes. Its bundle, world slice and corpus digests must equal the base's sealed ones, and `tree_sha256` must stay the base's. So the plaintext tree must really be published, because `--check` compares it with the tree on disk.
  - While the set stays in sealed custody, its sealed bundle, world slice and corpus digests and its `tree_sha256` never change. So a pull request cannot swap in an empty tree digest or a new slice.
  - `replaced_by` is set once and never changes. It must name a set that is in sealed custody and not retired, on the base as well as in the head (a live reseal already on main). So one pull request cannot add a successor and retire a live set onto it.
  - The manifest is never removed.
- If the base cannot be read (no `origin/main` or `main`, or no merge base), the check fails. Run `git fetch origin main` and try again. CI checks out full history, so it always has the base.
- `tests/sealed-governance.test.ts` runs the same check on the checkout, so `bun test tests/` in CI enforces it too.

**Backup records.** `sealed/backups.json` on main lists the sha256 of the backup each set was sealed from, with a short note on where it came from. `seal.ts --from-backup` adds the entry to the checkout, and the custodian commits it with the manifest. Before it decrypts anything, it refuses a file that does not parse or has a malformed entry, and a backup that the checkout or main already records for another set. The access log's `sealed` line records the backup's sha256 as `source_sha256`, and under the custody lock the seal refuses a backup that another set's `sealed`, `reencrypted` or `compared` line already names, so two seals of one backup under different names cannot both land before either entry reaches main. If the file cannot be written after a seal, it prints the entry to add by hand. The v0.3 entry (internal-task's gen5 backup) and the v0.3-gen6 entry (gen6) were added by hand. `--check` refuses an entry that names no set, a digest that is not 64 lowercase hex characters, a missing note, and a backup recorded twice. The file is append-only: every entry on the base must still be there with the same set, sha256 and note. A base file that does not parse fails the check.

**rekey.ts and compare-backups.ts bind each backup to `--set` by that file on main.** They read it from main fetched from the custody remote, with the shared-set check, before anything is decrypted.
- rekey's backup and compare's `--a` bind when the file records them for `--set`, or for a set whose `replaced_by` chain reaches `--set` (the set a reseal replaced). A replaced set's backup is refused while another live set, besides `--set`, shares the replaced set's slice or corpus, on main or in the `--repo` checkout. It is also refused when the replaced set has an `opened` run or a `released` line.
- compare's `--b` binds only when the file records it for `--set`.
- A backup recorded for any other set is refused, even with `--declare-backup`.
- A `sealed` line's `source_sha256` in the access log counts as a record for that line's set, so a backup another set was sealed from is refused before its `sealed/backups.json` entry reaches main.
- A file on main that records one sha256 more than once is refused. A backup belongs to one set.
- A backup recorded for no set is refused unless the custodian names its sha256 with `--declare-backup <hex>` (repeatable on compare). The access-log line then lists it under `declared_sha256`, so the binding is on record. A declared backup that is also recorded is listed too.
- The binding runs again, against main fetched fresh, in the push decision under the custody lock. So a record that lands while the backup is decrypted is seen before anything is written or printed.

## Repo-kind sets (internal-task)

**A repo set is a held-out set of repository tasks** (the gstack-native format, `tasks/repo/<set>/<split>/<task-id>/`). It goes through the same custody chain as a multi-user set. The differences:

- **It has no world.** No world slice, no corpus pages. Its `MANIFEST.json` says `"kind": "repo"` and records `world_manifest_sha256`, `world_json_sha256`, `sealed.world_slice_sha256` and `sealed.heldout_corpus_sha256` as `null`, with `sealed.null_digests` saying why. A change to `world/seed/` never touches a repo set.
- **Where it lives.** The public dev split is `tasks/repo/<set>/dev/`. The manifest is `tasks/repo/<set>/heldout/MANIFEST.json`, and that directory never holds anything else, sealed or released. `bun scripts/seal-heldout.ts --check` finds repo sets beside multi-user ones and fails on any other file there.
- **Set names are unique across kinds.** `--check` fails when `tasks/multiuser/<name>/` and `tasks/repo/<name>/` both exist, and seal.ts refuses a name the other kind uses. Every custody path, ledger row and preregistration names a set by name alone.
- **The openings ledger is the same.** `opening_budget`, `alpha_per_opening`, ledger rows and the HE-HELDOUT checks count a repo set exactly as they count a multi-user set (`runner/heldout/openings.ts`).

The steps:

1. **Seal.** `bun scripts/sealed/seal.ts --kind repo --task-set <set> --tasks <dir> [--generator <dir>] [--include <path> ...]`, with no `--slice` and no `--corpus` (both refused). `--generator` packs the set's generator at `generator/` in the bundle and commits its digest as `sealed.generator_sha256` (null without one). Each task's task.toml must name a `kind` of fix, review, qa or ship (export counts repo tasks by kind), and each task's `environment/Dockerfile` must end with the instruction `LABEL harness-eval.sealed=true`, exactly that line, as an instruction of its own (cleanup finds held-out images by that label; as the last instruction it is in the final stage and nothing overrides it; seal.ts checks this form and fails closed, so any other placement counts as unlabelled. A held-out task's Dockerfile also has no heredoc: `<<` on any line but a comment refuses it, because a label line inside a heredoc body never reaches the image. Its first instruction is FROM or ARG, an escape directive is the backslash, a syntax directive names docker/dockerfile only, and the file is printable ASCII with LF or CRLF line ends. Build options can still drop the label (a `BUILDKIT_SYNTAX` build argument, `--target`, `--label`), so the bridge that builds task images must pin them); seal.ts refuses the set otherwise. Regular files only, and a file's executable bit is kept (verify.sh, solve.sh, build scripts); every existing refusal holds: inputs inside the checkout, symbolic links, plaintext of the set in the checkout, the recipient checks, the private-repository check. `--from-backup` works the same way, with `--generator` as a path inside the backup.
2. **Open.** open.ts admits the opening exactly as before, then decrypts into the sealed root: `tasks/repo/<set>/heldout/`, `generator/`, `extras/` and `opaque-salt`. Files are written 0600, executables 0700, so a bridge that builds a task image from the root sets the modes its image needs. It skips the world merge and the world check, verifies the tree, generator and task count against the commitments, and writes a receipt with `"kind": "repo"` and null world digests. **It does not hand off to `runner/run.ts`**: it prints the access-log line and one line with the root's path and counts, and the bridge that runs repository tasks reads the root. Resume works as before.
3. **Export.** export.ts runs unchanged on a repo root. Repo tasks are counted under their task.toml `kind` (fix, review, qa, ship). The generator's files are sealed text for the output guard and the leak scan: every line, quoted string (also with escapes such as `\u002d`, `\055` and an escaped line break decoded) and JSON string in them. A value a generator builds at run time is not covered, so keep secrets out of generator code or pass them as an extra.
4. **Cleanup.** For a repo set, cleanup.ts always removes the docker images labelled `harness-eval.sealed=true` and the build cache, `--images` or not, since task images hold task bodies. Harbor job directories (each directory under `jobs/` of the root or a `--results` directory) go with the directory that holds them. Harbor writes `jobs/` where it runs, so a top-level `jobs/` in the checkout is ignored by git and refused by the publication check and `gstack-pregate sealed`. Before removing anything it writes an inventory (every job directory path, every sealed image id and tag) to `~/.capy/work/custody/logs/cleanup-<epoch ms>-<pid>.log` (0600) and prints only counts and that path.
5. **Release.** release.ts writes the task tree to `tasks/repo/<set>/released/` and the generator, extras and salt to `tasks/repo/<set>/sealed-bundle/`, checks the generator digest instead of a slice and corpus, and leaves `heldout/` holding `MANIFEST.json` alone.

**Claims across arms.** A repo run compares arms (for example none, gstack and placebo) per model. `scripts/compare-run.ts` compares every pair of cells as b minus a, with a before b in the manifest's cell order (the preregistration's), paired by task and repetition. A claim names any two cells as `where: {"a": <earlier cell>, "b": <later cell>}`. CI, open.ts and export.ts refuse a claim that names its cells the other way round.

**Gates.** A claim may carry `requires_gate: {"file": "<name>.json", "key": "<model>"}`. The file is a JSON object at the top of the raw results, one entry per key, each with a boolean `pass` (for example `gates.json` `{"<model>": {"body_load_rate": 0.9, "pass": true}}`). When the key's `pass` is false, the claim is **dropped from its Holm family** before the correction and published as `dropped`, "not measuring skill bodies". A missing file, key or boolean `pass` refuses the export before anything is pushed. A gate file may not be named `summary*.json` or `comparisons*.json`, which export.ts rewrites. A `secondary` claim's decision publishes its accept or reject bit and its wording only, in every mode: no estimate, interval or p. In full mode the per-cell and per-task results stay published for every cell, so a reader can still compute a secondary pair's difference as a descriptive number.

## Main never receives custody material

For any push or pull request bound for main, whatever the repository's visibility:

- `gstack-pregate sealed` (run by /ship before every push) refuses `*.age` and `access-log.jsonl` anywhere, raw receipts under `sealed-results/`, every path under `tasks/repo/*/heldout/` and `tasks/multiuser/*/heldout/` but `MANIFEST.json` (`sealed.allow_paths`, which needs gstack 1.91.311.0 or later; `.gstack/ship-policy.json` sets `min_gstack_version` to 1.94.4.0, which also covers pregate's `timeout_s`), and any added line holding an age identity (`AGE-SECRET-KEY-1` and 58 bech32 characters). `.gstack/pregate.json` sets `"visibility": "public"`, so a private repository refuses as well instead of warning.
- `bun scripts/check-sealed-publication.ts` (run by `tests/sealed-publication.test.ts`, so CI checks every pull request to main) refuses the same files and identities, a `results/manifest.json` planned with a sealed root while its set is still sealed, any file under `docs/benchmarks/<run>/results/` of a run whose `prereg.json` opens a set that is still sealed, anything in `sealed-results/` beyond the three export files, and a sealed set's released files before release. For repo sets it refuses any file under `tasks/repo/<set>/heldout/` but `MANIFEST.json`, whatever the manifest says, and `tasks/repo/<set>/released/` and `sealed-bundle/` while the set is sealed.
- Pushes to the custody ref go through the separate validator in `scripts/sealed/custody.ts` (`bun scripts/sealed/custody.ts --validate <clone> --base <commit>` checks a change by hand).

Artifact allowlist: only the three exported public files (`export.json`, `opening-receipt.json`, `README.md` under `sealed-results/`) may go into ship or review artifacts, project handoffs, prompts, reports or attachments. Raw results, logs, the opened root, the custody branch's files and the identity never do.

## Budget and decisions

A sealed set gets two confirmatory openings at alpha 0.025 each. Holm runs within each claim family of an opening (primary, and secondary when the preregistration names any): the opening's alpha is split across the claims of one family, superiority and noninferiority alike. With two families, an opening's chance of at least one false acceptance can reach 0.05 (0.025 per family), so a secondary claim's decision is published without its estimate, interval or p. The second opening is only for a candidate that failed at opening 1, was fixed on dev data and re-preregistered under a new run id; its proposer is told one accept or reject bit per claim from opening 1 and nothing else. Rules the code enforces:

- Openings are counted from the custody access log, not from the public ledger's current status. A row that is withdrawn or superseded after its opening never refunds it, and `bun runner/prereg/prereg.ts` fails when a run has a published `sealed-results/opening-receipt.json` and its row is not `opened`.
- A candidate (by `candidate_sha256`) gets at most one confirmatory opening of a set.
- A dev opening needs a reason, as for plaintext sets, and is logged like any other opening.
- Every claim in the preregistration's `heldout.claims` is a decision. A claim's `family` is `primary` (the default) or `secondary` (internal-task), and Holm runs within each family at the opening's alpha; with no `family` field, all claims enter one Holm family, as before. A claim whose gate failed enters no family (Repo-kind sets, "Gates"). A superiority claim enters with its two-sided p and is accepted when its Holm-adjusted p is at most alpha and the estimate points in the claimed direction. A noninferiority claim enters with its one-sided p against the preregistered margin, which `scripts/compare-run.ts --margin <a>,<b>,<margin>,<higher|lower>` computes from the same cluster bootstrap as the interval (export.ts passes one per claim), and is accepted when its Holm-adjusted p is at most alpha. A comparison that `heldout.claims` does not list is descriptive: it is not a claim and enters no family. A `secondary` claim is a claim, decided in its own family.


## What an opening publishes

`docs/benchmarks/<run>/sealed-results/` holds three files:

- `export.json`: run, set, opening number, label and reason, mode, the budget state, one accept, reject or dropped (a failed gate) per preregistered claim with its decision sentence, and its family when an opening has more than one family or a dropped claim (a secondary claim's decision carries no estimate, interval or p in any mode), trial counts (planned, recorded, scored, excluded), spend, and the sha256 of the opening receipt, the bundle, the raw results bundle and each raw receipt file.
- `opening-receipt.json`: digests only.
- `README.md`: the decision sentences in plain words.

While the set's reserve opening is unused (fewer confirmatory openings in the access log than the budget, and the set not retired), the export is in embargo mode: decision bits, counts, spend and digests only, and each decision sentence is the claim id, accepted or rejected, and the preregistered claim sentence, with no estimate, interval or p. After the last opening the export is in full mode and adds per-cell aggregates and per-task counts under opaque ids (below; the salt that maps them back stays sealed until release). `--mode embargo` forces the embargo; full mode cannot be forced. Before anything is written, a leak scan refuses the export if any task id, task string, hidden fact, slice string, corpus line or raw summary string of eight characters or more (absent from the public world, preregistration and manifest) appears in a public file; the refusal names the file and the kind, never the text. Per-task diagnostics, transcripts and trial records come out only at release.


## What may print

Any agent thread, and any gbrain or gstack thread, can read another thread's transcript. Whatever a custody command prints, whatever an agent reads into its context, and whatever goes into a brief, a report, a subagent prompt or an error message is therefore as good as published. The rule:

- No task body, hidden fact, world-slice or corpus content, task id or per-task diagnostic reaches the stdout or stderr of a custody command. That covers `seal.ts` (with or without `--from-backup`; a refusal prints its code, a count and the log path), `open.ts`, `runner/run.ts` plan, dry-run, preflight and run, `scripts/run-shard.sh` and the Ubicloud lane's streaming (a sealed lane's poll lines carry the trial count only, never a shard-log line), `build-gbrain-image.sh --sealed-root`, `merge-shards.ts`, `summarize-run.ts`, `compare-run.ts`, `export.ts`, `keygen.ts`, `cleanup.ts`, `rekey.ts`, `compare-backups.ts`, and `release.ts` before the release lands. A parser's error message quotes the bad input, so the custody scripts print only the error's class for anything that is not a coded refusal, and a results file or receipt that is not JSON is HE-RUN-007 naming the file, the line number and the error class.
- What may print: digests, counts, run and cell ids, paths, opaque task ids, progress counts and the allowlisted aggregate (the decision bits and sentences an export publishes).
- Tasks are named by opaque id. The bundle holds `opaque-salt`, a random value written at sealing; a task's opaque id is `T-` and the first ten hex characters of sha256 of the salt, a newline and the task id. The ids are stable for the life of the set, the same in every log line and in a full export's per-task counts, and they map back to tasks only once the salt is released with the set.
- Per-task tables and logs go to files under the raw results or the sealed root only: `<results>/sealed-console.log` (plan, preflight and run), `<root>/logs/dry-run.log`, `<out>/merge-shards.sealed.log`, `<results>/summarize-run.sealed.log` and `compare-run.sealed.log`, `<results>/export.*.log`, `<root>/logs/build-gbrain-image.log` (for a build run by `scripts/run-shard.sh`, `<out>/sealed-root-logs/build-gbrain-image.log`), and seal.ts's `~/.capy/work/custody/logs/seal-<epoch ms>-<pid>.log` (directory 0700, file 0600). A seal.ts refusal prints only its code, its problem count and that log's path. A failed step in a sealed shard or a sealed image build prints the log's path, never its last lines.
- An error message names an opaque id and a file path, never content. Under a sealed root, an error whose code carries only paths, digests and counts (HE-SEALED, HE-HELDOUT, HE-BUDGET, HE-PREREG, HE-PIN and the usage codes) prints with task ids replaced by opaque ids; any other code prints the code, the opaque ids it names and the log file, and its text goes to the log only. An uncaught error prints HE-SEALED-009 and the log path.

The runner and the two report scripts enforce this with an output guard (`runner/heldout/guard.ts`): every line still goes, whole, to the log file, the terminal gets only allowlisted lines with task ids and sealed strings replaced, and the number of withheld lines is printed at exit. `tests/sealed-output.test.ts` runs every custody command on a synthetic set, one sealed shard included, and fails if any of them prints a task id, body text, hidden fact or slice name.

What the code cannot enforce, the custodian thread follows:

- It never cats, greps, reads or opens a sealed file (the task tree, the slice, the corpus, `world/world.json`, trials.jsonl, turns, logs, the custody log files) into its own context. The scripts read them; the agent reads what the scripts print.
- Its briefs, reports, messages and subagent prompts carry only the aggregate: the decision bits and sentences, counts, spend, digests and paths. A subagent it starts follows the same rule and runs only the scripts.
- When a step fails, it reports the code, the opaque ids and the log path, and fixes the cause from the public code and the public files; reading the log is for a person on their own machine.


## The identity and its escrow

- `bun scripts/sealed/keygen.ts --check-escrow` fails (HE-SEALED-012, exit 2, nothing secret printed) unless the drive copy exists and derives `sealed/recipient.txt`, and `escrow/identity.age` on the custody ref decrypts under the passphrase derived from the current `UBICLOUD_API_KEY` (HMAC-SHA256 of the value over "harness-evals custody escrow v1") to an identity deriving the same recipient. open.ts and release.ts run the same check before they decrypt anything, so a stale escrow is found at the next opening, not on the day the drive copy is lost.
- `bun scripts/sealed/keygen.ts --restore` recreates a lost drive copy from the escrow, exclusively, and checks its recipient.
- Drive history keeps only about 24 hours, so durability rests on the escrow. Losing both the drive copy and the escrow (or the drive copy and every `UBICLOUD_API_KEY` value the escrow was made under) means generating a new identity and resealing the sets.
- An author's backup of a set's plaintext is encrypted to the committed recipient (`sealed/recipient.txt`), with its sha256 fingerprint checked against the one keygen printed (`9f8983d6bd0aa18a9fd779956013c9b8f19edad602507cdf4d3590040ad73439`), never kept as plaintext.

### Rotating UBICLOUD_API_KEY

The escrow passphrase is derived from `UBICLOUD_API_KEY`, so a rotation without this step leaves an escrow nobody can open. In order: rotate the key ([ubicloud](ubicloud.md#rotating-ubicloud_api_key)); while the drive copy is present, run `bun scripts/sealed/keygen.ts --re-escrow` with the new value in the environment (`--gh <path>` names the gh binary asked for the repository's visibility; default gh on PATH). It encrypts the drive copy under the new passphrase, decrypts the new escrow in memory and checks its recipient, and only then replaces `escrow/identity.age` in one validated custody commit (an `escrowed` line), pushed without force; the old escrow stays in the branch history. Then `bun scripts/sealed/keygen.ts --check-escrow` must pass. If the drive copy was lost first, run `--restore` under the old value before rotating.

## If the repository is to become public

The custody branch's ciphertext and escrow are only as hidden as the repository: if garrytan/harness-evals is ever made public, they go public with it. open.ts, export.ts, seal.ts and `keygen.ts --re-escrow` ask `gh api repos/garrytan/harness-evals -q .private` and refuse with HE-SEALED-013 unless the answer is `true`, and every custody fetch and push refuses a remote any of whose URLs is a network URL not naming that repository; an unreadable answer is a refusal. Before any visibility change:

1. Move the custody branch to a private repository (push `refs/heads/custody` there) or delete it, and confirm with `git ls-remote origin refs/heads/custody` that the public repository no longer has it. Deleting the branch does not remove its objects from GitHub's caches or from forks; treat everything that was on it as exposed once the repository is public.
2. If anything is to stay sealed: generate a new identity with keygen.ts, reseal each still-sealed set under it as a new set (new recipient, new bundle, new commitments), and re-escrow. The old recipient's ciphertext counts as published once the repository is public, since the old escrow is protected only by the `UBICLOUD_API_KEY` value.
3. Only then change the visibility. [publishing-checklist](publishing-checklist.md) carries the same step.

## What remains procedural

The scripts make the protocol checkable; these parts rest on the crew following it:

- The identity file is in the harness-eval project-user drive. It is not mounted by default outside the harness-eval project, and never on Ubicloud VMs, but any agent thread in this project could read it. Excluding candidate developers and the set author is procedural: a CREW rule, the scripts as the only reader, the output guard, and the access log.
- The access log records script-mediated openings only. Anyone who reads the identity and decrypts a bundle by hand leaves no line.
- The custodian thread runs the scripts without reading the identity, their plaintext inputs or logs into its context ("What may print"), and reports decision bits and the public export only. The scripts can withhold what they print; they cannot stop an agent from opening a file.
- A set author working in an agent thread would put the bodies into that thread's transcript, which the org can read. Sets are written where no agent thread can read them (for example on the author's own machine) and reach the custody pipeline only through `seal.ts`.
- The proposer of a second opening is told one bit per claim; nothing stops a person telling more.
- Set authors and candidate authors are different people or threads for a given set.
- The leak scan catches exact strings, not paraphrase. The custodian reads the export before committing it.
- Ubicloud VMs hold a copy of the root while a shard runs and are destroyed on every exit; the copy is as private as the VM.
- Access to the custody branch is GitHub's access control on the whole repository: anyone with read access to garrytan/harness-evals can fetch `refs/heads/custody`. The ciphertext is safe while the identity is; the escrow is as safe as the `UBICLOUD_API_KEY` value.
- The custody remote check allows exactly two hosts for `garrytan/harness-evals`: github.com and git.capy.ai, the git proxy for it (owner decision, 2026-10-28); every other host is refused. Custody fetches and pushes through git.capy.ai are as private as that proxy.
