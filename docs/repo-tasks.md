# Repository tasks

**A repository task gives a coding agent a real Python repository in a container and one job a lead engineer would hand over: fix a bug, review a change, find bugs in a running app, or get a branch ready to merge.** The grade comes from running hidden checks afterwards, in a separate clean container, never from what the agent says it did.

This page describes the format as of harness-evals v0.0.49 and the **gstack-native-v1** set (internal-task). The set exists to test, on tasks nobody tuned against, whether loading gstack's skills changes what Claude Code gets done compared with a length-matched placebo and with no skills (the Lane B design from gstack-evals). Multi-user tasks are a different format: [tasks.md](tasks.md).

## The set

- **Four kinds, one skill each.** fix (the skill called `investigate`), review, qa and ship. Each task names the gstack skill the gstack arm is told to use; the task text itself never mentions gstack.
- **Dev split, public: 8 tasks, two per kind**, in [tasks/repo/gstack-native-v1/dev/](../tasks/repo/gstack-native-v1/README.md). They are for calibration (the dev pilot) and anyone can read them.
- **Held-out split, sealed: 32 tasks, eight per kind.** Generated by the same recipe from a private seed and sealed with procedural custody ([sealed-custody.md](sealed-custody.md)) before any counted trial. Only `tasks/repo/gstack-native-v1/heldout/MANIFEST.json` is ever on main.
- **Source repositories.** Small, permissively licensed Python libraries pinned by commit. The dev split uses inflection, schedule and tabulate; the held-out split uses none of them. qa tasks use a small generated web app instead. License texts: [tasks/repo/gstack-native-v1/LICENSES/](../tasks/repo/gstack-native-v1/LICENSES/).
- **Generated, then checked.** A model writes each task's content (the planted bug, the defective change, the broken branch); fixed code assembles the containers, the verifier and the wrong-solution checks; the acceptance matrix below decides whether the task is used.

## What one task holds

`tasks/repo/<set>/<split>/<task-id>/`:

- `task.toml`: `id`, `kind`, `skill`, time and resource limits, `workdir = "/work/repo"`, `artifacts = ["/work"]`, and a `[score]` table per kind (qa: `planted_bugs`, `max_false_reports`; review: `planted_hunks`; ship: `allowed_paths`). `[source]` names the upstream repository, commit and license.
- `instruction.md`: what a lead would tell any engineer, including the output contract (findings file, repro directory, branch and remote). Nothing about gstack.
- `environment/`: the agent image. The Dockerfile pins the base image by digest, Debian packages by version from a dated snapshot of the Debian archive, and Python packages by hash (`requirements.lock`). The working tree (a git checkout, and for ship a bare remote) is `work.tar`, added at `/work/`, so the task tree holds no nested `.git`. Fixture commits carry a neutral identity and no reflogs.
- `verifier/`: the verifier image. Its Dockerfile builds the same toolchain with no starting `/work` and copies the verifier to `/tests`. `verify.sh` writes `/logs/verifier/reward.txt` (0 to 1) and `result.json` (bits and counts only).
- `oracle/solve.sh`: reaches reward 1 from the starting container.
- `checks/`: wrong solutions and tamper attempts, each run in place of the agent. Every one must score 0.

## How grading works

**The verifier never runs where the agent ran.** After the agent stops, only `/work` is copied out of its container (Harbor's `artifacts`, restored with the tar "data" filter, so absolute paths, path traversal and links out of `/work` are dropped). A fresh container from the verifier image, with no network, grades it. Anything the agent did outside `/work` (a fake `env`, a swapped `python3`, a reward file it wrote) is gone.

Inside the verifier, the agent's code runs only as `nobody`; the verifier itself, its hidden tests and the reference app copies are root-only. Before grading, `/work` and `/logs/verifier` become root-owned and read-only to `nobody`. Before and after every run of the agent's code, every `nobody` process is killed and every file and System V IPC object `nobody` owns is deleted, so nothing carries from one run to the next or outlives the grade. Per kind:

- **fix:** the repository's protected files are restored, pytest hooks the agent added are removed, and the repository's tests run as `nobody`. The grade reads pytest's junit report, not its exit code. No repository test may fail, and the repository test count and skips must match what the oracle produced. A run that exits early writes no report and fails.
- **Hidden tests (fix and ship) never run beside the agent's code.** A trusted pytest, as root in a directory `nobody` cannot read, runs them against a stand-in for the library. Each library call goes over a pipe to a worker that imports the agent's library as `nobody`. Only the return value (a Python literal) and the arguments' values after the call come back. So the agent's code never sees the tests, the expected values or pytest, and cannot change a verdict. Every hidden test must pass, with the expected number of parametrized cases.
- **review:** each finding's test must fail on the defective change and pass on the corrected one, and its location must fall in a planted hunk. Both changes run at the same path, one after the other, so a test cannot tell them apart by where it runs. Reward is found over planted, and it is 0 if any listed test passes on the defective change or the list holds more than 10 findings.
- **qa:** each repro must show the bug on the buggy build and not on the fixed build, on every one of `repro_runs` runs. Every build runs from the same path with the same arguments, owned by root and unreadable to the repros. Reward is reproduced over planted; 0 if false reports exceed `max_false_reports` or there are more than 10 repros.
- **ship:** the named branch exists on the remote, main has not moved, the branch merges cleanly into main, and it touches only the feature's files plus `allowed_paths`. Lint and the CONTRIBUTING check (a new bullet under `## Unreleased` in CHANGELOG.md) run before any of the branch's code. Then the tests run as for fix.

<details><summary>The wrong-solution and tamper checks</summary>

- **Every kind:** noop (the agent does nothing); shim (a reward file plus an `env`, `python3`, `node` and `git` that always succeed, all in the agent container, and no work).
- **fix:** two plausible wrong fixes; hooks (a conftest that skips every test and edited test files); pyexit (the real fix, plus a package that exits with status 0 as soon as pytest imports it); flipreport (no fix, plus a package that rewrites every failing pytest report as passed).
- **review:** always-pass test; wrong place; cwdsniff (a test that passes or fails by where it runs); spray (the real finding plus nine whose tests pass on the defective change); crossrun (a test that fails on its first run and passes later, using a marker file); linger (a test that leaves a process behind to rewrite the reward and findings files).
- **qa:** false alarm (the real repros plus two that always fail); cmdsniff (repros that look for the build's name in process command lines); srcsniff (repros that try to read the app or verifier files); counter (repros that pass their first runs and fail later ones, counting in a file).
- **ship:** force-push main; no changelog bullet; push without merging main; an unrelated change; pyexit (the finished branch plus a package that exits with status 0 under pytest); flipreport (the branch without the feature, plus a package that rewrites failing pytest reports as passed).

**Known limit:** the repository's own tests still run with the agent's code in the same process. An agent that rewrites pytest verdicts could hide a regression in a repository test. It cannot fake the hidden tests, which decide whether the fix or feature is there. Hidden tests can only call functions that take and return Python literals.

</details>

## Acceptance

A task is used only when all of these hold. Every check prints counts and bits only.

- `bun scripts/repo-tasks/matrix.ts --task <dir>` runs each scenario the way a Harbor trial with separate verification does: the script runs as root in an agent container with `/oracle` and `/checks` copied in, `/work` is copied out, and a fresh verifier container grades it. The oracle must score 1 on 5 of 5 runs; the starting state and every `checks/` script must score 0 on 5 of 5. The dev split's results, with the image ids they ran on, are in `tasks/repo/gstack-native-v1/dev/ACCEPTANCE.json`.
- Lint is clean: no run of 8 words shared with any gstack `SKILL.md` body at gstack 61e201ec, no gstack-only skill name, no slash-prefixed skill name, no gstack marker and no author identity or host path, in the instruction, the Dockerfiles, the verifier, any text file of the working tree, and the commit identities and config of every repository in `work.tar`.
- qa only: Playwright launches against the app with the network off.

`tests/repo-dev-split.test.ts` checks the dev split in CI: two tasks per kind, the kind and skill pairing, `[score]` matching `verifier/task.json`, pinned base images, separate verification, executable scripts, no gstack marker or identity in the text files, Dockerfiles or `work.tar`, no reflogs, and an accepted matrix row for every task.

## Changelog

### 2026-10-29: first version (internal-task)

The repository task format and the gstack-native-v1 set's public dev split, so the dev pilot can calibrate the recipe before the held-out split is generated and sealed. Grading uses a separate verifier container because the first review found four ways to earn reward 1 without doing the work while the verifier ran in the agent's container.
